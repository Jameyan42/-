# 轻报：十分钟产品经理面试案例

## 一句话介绍
“轻报是我以 200 人成长型企业为场景，借助 AI 构建的费控网页原型。我围绕报销提交、审批、审核与付款设计闭环，并用规则预审和 OCR 辅助减少输入与核对负担。目前使用虚构数据，还没有真实客户或运营指标。”

请根据你本人实际参与的工作调整表述，不把 AI 完成的开发或虚构调研称为独立经历。

## 演示节奏
1. **0～1 分钟：问题**。说明三个角色和待验证痛点，不声称已经采访真实财务团队。
2. **1～4 分钟：主流程**。员工创建报销，主管通过，财务审核并填写模拟参考号完成付款登记。
3. **4～6 分钟：OCR 与异常**。新建报销载入虚构样票，观察真实识别结果；演示未确认不覆盖。解释这是输入辅助，不是验真或自动审批。
4. **6～8 分钟：取舍**。预算区分在途和实际，主管前可撤回，规则调整必须说明原因，日志可查看。
5. **8～10 分钟：验证与下一步**。展示项目案例、测试范围及待验证指标，说明为什么尚未接银行、税务或企业组织系统。

## 面试追问与回答要点
- **为什么做网页？** 多角色协作、低使用门槛和统一更新适合原型验证；当前并不具备真实多人同步。
- **为什么不全靠大模型？** 金额与状态转换需要确定性；OCR 只给候选，人确认后应用，审批仍由人负责。
- **如何判断有价值？** 先比较相同任务下的提交时间、返工次数和提示理解率。现在只有功能验证，没有业务提升数字。
- **为什么预算只预警？** 复杂额度规则可能阻断合理费用，原型先验证可理解性，再决定哪些情形硬拦截。
- **你做了什么？** 结合实际说明你确定的目标、作出的优先级取舍、亲自检查的场景和提出的修改意见，不只背代码功能清单。
- **最大不足？** 无真实用户研究、服务端身份与审计；通用 OCR 对复杂版式不稳定，尚无多样本准确率证据。
- **下一步怎么排？** 可用性测试 → 修正表单和提示 → 小范围票据测试集 → 再评估 PDF、后端与企业集成。

## 产品决策复盘
**决定一：先做可操作闭环。** 减少对大型竞品模块的照搬，以可追踪的状态和异常处理体现业务理解。

**决定二：引入浏览器 OCR。** 免费开源、图片本地处理，避免在原型阶段接触真实财务资料和服务密钥；代价是首载体积与通用识别局限。

**决定三：核对后应用。** OCR 不直接覆盖已有数据或提交，字段不确定时留空，避免把自动化演示当作可靠财务判断。

**决定四：保留失败路径。** 坏图、PDF、不识别、取消和手工填写均可继续；测试发现取消后的焦点问题并修正。

**决定五：分离发布与运行。** 云端本地地址不是公网网址，最终采用公开 GitHub Pages 分支发布；后续更新无需用户重复设置。

## 可分享成果
在线演示、产品需求、场景测试、OCR 设计、操作指南及网页“项目案例”的打印版。分享前使用虚构数据，真实试用反馈需另行征得参与者同意并记录。


## 可选扩展演示：事前管控（2 分钟）
员工创建 1000 元计划 → 主管批准并观察预算 → 关联 600 元报销 → 完成审核付款 → 员工结束申请 → 观察剩余 400 元释放。解释为何申请额度不能突破、部门预算只预警，以及为何退回报销不能把整笔申请预算释放。此场景使用虚构数据，不代表企业已经采用这套政策。

## 组织与审批配置的讲解（v0.8）

可以演示：“组织树维护归属和汇报，审批树依据单据条件决定路径。提交时把规则解析为具体人员并保留快照，避免员工换上级后旧单据突然换人。主管角色相同也不能跨节点处理；大额申请要经过直属主管和部门负责人，全部通过后才预留预算。”

可讨论的取舍：先用一个金额与类型条件、两条互斥分支和顺序节点验证路径；暂缓任意嵌套和会签。相同主管与负责人只审批一次，防止重复待办。发布前覆盖所有在岗员工，避免配置成功却无人可审；调整组织时保护在途审批和待付款责任人。当前仍为浏览器模拟身份，不能把原型节点控制描述为生产权限安全。

你可亲自验证：创建旧申请 → 修改林晓上级 → 创建新申请 → 分别查看两份路径。记录是否能完成操作以及哪里困惑，补充你的真实体验；不要把 AI 自动化测试写成真实用户调研。

## 从功能堆叠转向任务入口（v0.9）

可展示的改进：“报销与费用申请都有审批，但原来分散在两个页面。我把它们收敛成按具体人员展示的统一待办，保留原单据详情，减少寻找任务的入口切换。审批通过和登记付款仍是不同责任步骤，因此财务审核通过后，任务继续保留到付款登记完成。”

重点解释：侧栏数量统计当前身份全部可处理任务，列表筛选只改变显示范围；切身份清除筛选以避免误判无待办。旧记录没有可靠提交时间时明确显示缺失，不拿业务日期冒充提交时间。CSV 只导出当前筛选和身份范围。以上来自流程分析和自动化验证，不宣称已测得审批效率提升；实际价值仍需真实参与者试用。

## 从树形列表到管理画布（v0.10）

用户反馈组织树应更接近思维导图，便于管理员设置 CFO、部门总和员工。此次按这个明确反馈增加图形节点、连接线、侧栏编辑和快捷添加，并将岗位与系统角色分开。仅一位项目用户反馈，不能描述为已经完成多名企业财务人员的调研。

同时将部门业务审批、财务审核、总账复核和付款职责独立：总账需登记科目与核算归属，付款人员在工作台处理复核后的单据。旧路径用快照保留，新模板需先预览再发布，避免界面升级静默改变在途单据责任。没有把“总账复核通过”描述为真实系统入账，也没有把“付款登记”描述为银行扣款。

## 已办不是当前状态列表（v0.11）

“我已处理”按操作事件而非单据去重。一笔报销可能被退回、修改后重新提交并再次审批，因此要保留当时事项、金额、备注和结果，不能用当前金额覆盖过去处理。页面区分“处理后”和“当前状态”，旧日志缺少人员标识就不自动推断成某人的历史工作量。

可如实介绍：这是从审批闭环追踪需求推导的设计，已用退回重提、跨角色、总账和付款、备份恢复等场景验证，尚未证明真实用户使用效率提升。为了避免处理次数被误认为支出，不在已办页面合计历史金额；分页与导出范围分别说明。

## 图形化之后还要能找到人（v0.12）

组织图解决“看关系”，搜索定位解决“大图中找到目标”。本轮选择保留完整画布、通过搜索结果展开祖先并居中，而不把无关节点直接删出视图，避免上下级关系失去语境。部门结果明确切到归属图，路径导航区分汇报与归属。

可展示：先折叠 CFO，再搜索叶禾，仍能定位并看到完整上级路径；编辑岗位后尝试切页，取消提醒会保留修改。上述是原型交互与自动化测试证据，没有真实管理人员效率提升数据。
