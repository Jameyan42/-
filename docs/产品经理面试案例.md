# 轻报：十分钟产品经理面试案例

## 一句话介绍
“轻报是我以 200 人成长型企业为场景，借助 AI 构建的费控网页原型。我围绕报销提交、审批、审核与付款设计闭环，并用规则预审和 OCR 辅助减少输入与核对负担。目前使用虚构数据，还没有真实客户或运营指标。”

请根据你本人实际参与的工作调整表述，不把 AI 完成的开发或虚构调研称为独立经历。

## 演示节奏
1. **0～1 分钟：问题**。说明三个角色和待验证痛点，不声称已经采访真实财务团队。
2. **1～4 分钟：主流程**。员工创建报销，主管通过，财务审核并填写模拟参考号完成付款登记。
3. **4～6 分钟：OCR 与异常**。新建报销载入虚构样票，观察真实识别结果；演示未确认不覆盖。解释这是输入辅助，不是验真或自动审批。
4. **6～8 分钟：取舍**。预算区分在途和实际，主管前可撤回，规则调整必须说明原因，日志可查看。
5. **8～10 分钟：验证与下一步**。展示项目案例、测试范围及待验证指标，说明为什么尚未接银行、税务或企业组织系统。

## 面试追问与回答要点
- **为什么做网页？** 多角色协作、低使用门槛和统一更新适合原型验证；当前并不具备真实多人同步。
- **为什么不全靠大模型？** 金额与状态转换需要确定性；OCR 只给候选，人确认后应用，审批仍由人负责。
- **如何判断有价值？** 先比较相同任务下的提交时间、返工次数和提示理解率。现在只有功能验证，没有业务提升数字。
- **为什么预算只预警？** 复杂额度规则可能阻断合理费用，原型先验证可理解性，再决定哪些情形硬拦截。
- **你做了什么？** 结合实际说明你确定的目标、作出的优先级取舍、亲自检查的场景和提出的修改意见，不只背代码功能清单。
- **最大不足？** 无真实用户研究、服务端身份与审计；通用 OCR 对复杂版式不稳定，尚无多样本准确率证据。
- **下一步怎么排？** 可用性测试 → 修正表单和提示 → 小范围票据测试集 → 再评估 PDF、后端与企业集成。

## 产品决策复盘
**决定一：先做可操作闭环。** 减少对大型竞品模块的照搬，以可追踪的状态和异常处理体现业务理解。

**决定二：引入浏览器 OCR。** 免费开源、图片本地处理，避免在原型阶段接触真实财务资料和服务密钥；代价是首载体积与通用识别局限。

**决定三：核对后应用。** OCR 不直接覆盖已有数据或提交，字段不确定时留空，避免把自动化演示当作可靠财务判断。

**决定四：保留失败路径。** 坏图、PDF、不识别、取消和手工填写均可继续；测试发现取消后的焦点问题并修正。

**决定五：分离发布与运行。** 云端本地地址不是公网网址，最终采用公开 GitHub Pages 分支发布；后续更新无需用户重复设置。

## 可分享成果
在线演示、产品需求、场景测试、OCR 设计、操作指南及网页“项目案例”的打印版。分享前使用虚构数据，真实试用反馈需另行征得参与者同意并记录。


## 可选扩展演示：事前管控（2 分钟）
员工创建 1000 元计划 → 主管批准并观察预算 → 关联 600 元报销 → 完成审核付款 → 员工结束申请 → 观察剩余 400 元释放。解释为何申请额度不能突破、部门预算只预警，以及为何退回报销不能把整笔申请预算释放。此场景使用虚构数据，不代表企业已经采用这套政策。

## 组织与审批配置的讲解（v0.8）

可以演示：“组织树维护归属和汇报，审批树依据单据条件决定路径。提交时把规则解析为具体人员并保留快照，避免员工换上级后旧单据突然换人。主管角色相同也不能跨节点处理；大额申请要经过直属主管和部门负责人，全部通过后才预留预算。”

可讨论的取舍：先用一个金额与类型条件、两条互斥分支和顺序节点验证路径；暂缓任意嵌套和会签。相同主管与负责人只审批一次，防止重复待办。发布前覆盖所有在岗员工，避免配置成功却无人可审；调整组织时保护在途审批和待付款责任人。当前仍为浏览器模拟身份，不能把原型节点控制描述为生产权限安全。

你可亲自验证：创建旧申请 → 修改林晓上级 → 创建新申请 → 分别查看两份路径。记录是否能完成操作以及哪里困惑，补充你的真实体验；不要把 AI 自动化测试写成真实用户调研。

## 从功能堆叠转向任务入口（v0.9）

可展示的改进：“报销与费用申请都有审批，但原来分散在两个页面。我把它们收敛成按具体人员展示的统一待办，保留原单据详情，减少寻找任务的入口切换。审批通过和登记付款仍是不同责任步骤，因此财务审核通过后，任务继续保留到付款登记完成。”

重点解释：侧栏数量统计当前身份全部可处理任务，列表筛选只改变显示范围；切身份清除筛选以避免误判无待办。旧记录没有可靠提交时间时明确显示缺失，不拿业务日期冒充提交时间。CSV 只导出当前筛选和身份范围。以上来自流程分析和自动化验证，不宣称已测得审批效率提升；实际价值仍需真实参与者试用。

## 从树形列表到管理画布（v0.10）

用户反馈组织树应更接近思维导图，便于管理员设置 CFO、部门总和员工。此次按这个明确反馈增加图形节点、连接线、侧栏编辑和快捷添加，并将岗位与系统角色分开。仅一位项目用户反馈，不能描述为已经完成多名企业财务人员的调研。

同时将部门业务审批、财务审核、总账复核和付款职责独立：总账需登记科目与核算归属，付款人员在工作台处理复核后的单据。旧路径用快照保留，新模板需先预览再发布，避免界面升级静默改变在途单据责任。没有把“总账复核通过”描述为真实系统入账，也没有把“付款登记”描述为银行扣款。

## 已办不是当前状态列表（v0.11）

“我已处理”按操作事件而非单据去重。一笔报销可能被退回、修改后重新提交并再次审批，因此要保留当时事项、金额、备注和结果，不能用当前金额覆盖过去处理。页面区分“处理后”和“当前状态”，旧日志缺少人员标识就不自动推断成某人的历史工作量。

可如实介绍：这是从审批闭环追踪需求推导的设计，已用退回重提、跨角色、总账和付款、备份恢复等场景验证，尚未证明真实用户使用效率提升。为了避免处理次数被误认为支出，不在已办页面合计历史金额；分页与导出范围分别说明。

## 图形化之后还要能找到人（v0.12）

组织图解决“看关系”，搜索定位解决“大图中找到目标”。本轮选择保留完整画布、通过搜索结果展开祖先并居中，而不把无关节点直接删出视图，避免上下级关系失去语境。部门结果明确切到归属图，路径导航区分汇报与归属。

可展示：先折叠 CFO，再搜索叶禾，仍能定位并看到完整上级路径；编辑岗位后尝试切页，取消提醒会保留修改。上述是原型交互与自动化测试证据，没有真实管理人员效率提升数据。


## v0.13：按日期回看已处理记录

审批中心 → 我已处理，支持起止日期（可只填一端）与今天、近7天、本月、上月、不限日期快捷选择。处理时间按当前浏览器本地时区划分日期，包含起止两天；近7天含今天，本月至今天。概览与页签保持本人全部处理次数，日期提示及页脚显示当前匹配次数，二者不混用。

日期与类型、结果、关键词共同筛选；改变日期回到第一页。CSV导出全部匹配页，并追加本地处理日期、筛选起止日期和时区，保留原始ISO处理时间。起止倒置时显示错误、禁用导出并标记结果未计算。清除筛选、切换身份/页面/待办页签或刷新会清空日期，不写入业务数据。

演示：赵航实际通过一笔报销 → 我已处理 → 今天，看到本人操作 → 改为上月观察空结果 → 填反起止日期观察错误 → 清除筛选恢复。没有真实历史日期时不要编造上月业务记录。生产权限、服务端统一业务时区、报销发生日期筛选和跨用户统计尚未实现。


## v0.14：员工报销进度总览

入口：选择员工角色及具体人员 → 报销进度（员工工作台也提供入口）。按流转中、待我完善、已登记付款分组；卡片显示申请金额、当前节点、当前待处理人、提交时流程版本和有序路径。搜索事项/单号/状态/节点/待处理人，每页10条；改变分组或搜索回到第一页，切身份/页面清空筛选。概览数字始终为本人全部报销，匹配数单独显示。

快照单据按申请人ID归属；无快照旧单/草稿仅在姓名唯一且部门匹配时归属。不按当前组织推测旧单审批人。当前具名路径来自提交快照，人员已停用/缺失或角色变化会提示核对，不自动改派。草稿/撤回/退回归入待我完善，退回显示最新可用说明，经查看详情可修改重新提交；重提后采用新快照。已付款不再显示待处理人，也不表示真实银行到账。

演示：林晓提交200元报销 → 报销进度查看赵航及后续周宁 → 赵航退回并注明补充用途 → 林晓在待我完善查看原因并修改提交 → 回到流转中。财务分工模板下叶禾的单据可依次显示沈岚、周宁、高璇和杜川。不要用演示身份选择宣称具备生产认证；当前没有催办消息、处理SLA、到账确认或事前申请进度总览。


## v0.15：差旅行程、费用明细与示例标准

本轮连通三个功能：出差申请补充出发地、目的地、出发/返回日期、城市档和示例职级档；差旅报销可启用1～20行费用明细（城际交通、住宿、餐补、市内交通、其他），自动合计；按固定版本示例标准检查住宿和餐补，超标说明必填后交由人审核。新增只读“差旅标准”页解释金额及口径。

员工 → 费用申请 → 新建，勾选“这是出差行程申请”；按原申请审批路径批准并预留预算。员工新建报销，选择本月已批准申请时自动载入行程并启用差旅明细；报销的行程和批准申请必须一致，关联金额仍受剩余额度硬限制。未关联申请也可手动启用差旅明细。旧普通报销不强制补填。

示例演示：林晓申请杭州至上海10月21～23日、2000元；赵航批准。关联报销填住宿1000元/2晚、餐补300元/3天、城际交通200元，自动合计1500元；主管→财务审核→模拟付款，申请剩余500元，付款后可结束申请释放未用余额。另填住宿1100元/2晚，显示超过500元/晚，要求说明后提交，审核人在详情查看超标与理由。

这是自定义示例制度，不代表法定标准或真实企业政策。城市/职级档手工声明，未接HR；标准只读，版本travel-demo-2026-01。住宿按实际晚数、餐补按含首尾自然日；重复住宿/餐补日期、越界日期、合计不一致会被拒。跨月行程暂需拆分，批准申请只在报销归属月份一致时可关联；报销日期仍沿用原提交/原单日期，不按行程自动改预算月份。

超标说明不自动豁免审批或原有单笔上限、缺附件、重复号码检查。明细行金额是行合计，不支持逐票附件、多票OCR、发票验真、自动订票或真实支付。启用差旅后的草稿也需完整行程及明细；可关闭差旅模式继续普通草稿。JSON备份保留行程、明细、理由和版本，非法合计/行程拒绝导入且不覆盖原数据。


## v0.16：费用申请进度与额度追踪

员工 → 申请进度（费用申请列表也有入口）。按待审批、已批准、已驳回、已关闭和计划月份筛选，搜索事项/单号/费用类型/目的地/当前审批人；每页10条，改变筛选回到第一页，切页面或身份清空筛选。概览始终统计本人全部申请，当前匹配数单独显示；导出CSV包含全部匹配页和本次筛选条件。

待审批按提交快照展示具体人员和顺序节点；旧申请只显示原主管角色，状态与路径不符时不猜处理人。批准后显示已占用额度、在途报销、已登记付款、未使用额度、当前可关联和余额预留。已占用=在途+已登记付款，草稿/退回/撤回不占额度。只有已批准的未使用余额可关联并预留；关闭或驳回的未使用金额仅供回顾，当前可关联和预留均为0。付款登记仍不等于银行到账。

卡片可展开本人关联报销并打开详情，显示不占额度的退回/撤回/草稿；从申请详情按原规则结束申请，仍有在途报销则不能结束。驳回显示原因，本版申请仍不可修改重提，可另行创建。出差申请展示已有行程。新记录按申请人ID归属，旧记录以唯一姓名和部门兼容；申请详情增加本人校验，演示身份不等于生产认证。

演示：林晓申请1000元→赵航批准→关联600元报销；申请卡片在途600、可关联400、余额预留400。员工撤回600元，卡片在途0、可关联1000；结束申请后未使用1000仍可回顾，但当前可关联/余额预留均0。另一条路线完成模拟付款后显示已登记付款600、余额预留400，结束只释放400。申请批准不等于已支出1000，不将原额度与在途重复计入预算。

页面为只读进度与现有操作入口，不迁移或清理数据。存储损坏明确提示且不展示假完整概览/导出。没有催办、自动超时、消息通知、跨设备同步或生产访问控制；筛选和导出不写入业务数据。


## v0.17：报销多附件与证明材料

新建/编辑报销 → 报销附件 / 证明材料，可多选上传PDF、PNG、JPG、WebP，并分别标为发票、酒店水单、行程单、付款凭证或其他材料。每单最多5个，单个1 MB、合计1.5 MB；为浏览器演示版容量限制。原文件保存在报销记录中，不上传外部服务；保存草稿、刷新、退回修改后仍保留。旧“发票OCR / 原票据名称”入口继续兼容，但该入口本身仍只记录名称；需保留原文件时使用新附件区。

报销详情向员工和审核人展示附件分类、名称、大小。图片可展开预览；所有支持文件可下载原文件，PDF下载后由浏览器/阅读器查看。审批详情不提供移除按钮；员工在可编辑状态移除已保存附件时会确认，只有再次保存报销才生效，关闭未保存表单仍有提醒。台账可索引和搜索新附件名称，再跳转报销详情查看。

“发票”类附件可满足原附件完整性检查，酒店水单/行程单等不自动替代发票；原发票号码查重仍按整单号码，附件不自动识别多票号码或金额，不代表票据验真。差旅明细仍共用整单附件，尚未逐行绑定或逐票OCR。

完整JSON备份包含附件原文件（编码保存），恢复后仍可下载；旧仅名称记录不补造文件。导入检查分类、数量、扩展名/类型、文件头、编码、大小与单据总容量，非法数据不覆盖原数据。备份仍限制5 MB；浏览器总容量不足会提示。保存报销先写成功再更新内存；备份多键恢复写入失败时尝试回退已写入键，原测试数据回退已验证，异常无法回退时明确提示。

演示：员工填写200元报销，旧OCR入口选择发票；新附件区上传虚构酒店水单PDF和行程截图PNG，分类后保存草稿。刷新再编辑提交，切主管查看两份材料，展开图片并下载PDF。导出备份并在独立测试环境恢复，原PDF字节一致。请用虚构材料，备份含原文件，应由用户自行保管。

当前为本浏览器本地存储，不跨设备同步；清理浏览器数据会丢文件。图片只支持预览，不编辑原图；PDF不内嵌预览。文件头检查不是恶意文件扫描，也不能保证票据真实。没有云文件服务、细粒度下载授权、加密存储或永久留存承诺。


## v0.18：付款清单、重复参考号与批量模拟登记

付款工作台新增当前筛选清单CSV导出、勾选/清空和批量模拟付款。只可选择本人有权限的待付款单据，每批1～20笔，切筛选/搜索/页面/身份会清空勾选；超过20笔需缩小查询或手选。管理员仍只读。原搜索支持事项、单号、申请人、部门和参考号，导出包含当前筛选的所有记录，不只勾选项。

点击批量模拟登记，预览逐笔事项、金额、单号和参考号，并填写日期、方式、备注。前缀为3～48位字母/数字/下划线/短横线，每笔生成“前缀-001”等独立模拟参考号；明确确认仅模拟后才能提交。重新校验所有所选单据的状态、具体付款权限、schema2总账信息、预审风险、参考号和付款字段，其中任一失败整批不保存。单键保存成功后才更新界面；容量不足保留原单据及核对表单，可减少问题后重试。

单笔和批量新登记都会与当前浏览器全部已付款记录核对参考号，忽略首尾空格及大小写，重复时拦截；不回改或删除旧重复记录。此为本原型一单一参考号的规则，真实企业一个银行交易关联多张报销等场景需要另建付款批次/交易模型，当前不代表银行幂等机制。

成功后每笔报销保留独立付款信息和具名处理记录，批量操作另记一条操作日志，刷新与完整备份兼容。导出包含部门、申请人、金额、状态、付款责任人、总账科目、核算归属、付款日期/方式/参考号及筛选条件。仅是模拟登记，不连接银行、不确认到账、不生成实际银行付款文件。

演示：按已有财务分工模板提交两笔200元报销，经部门负责人、财务、总账完成后切杜川→付款工作台，勾选两笔→预览合计400和两个参考号→确认模拟→查看已付款及审批中心我已处理两条记录→导出清单。再以相同前缀登记新单据，观察重复拦截；核对失败不部分登记。旧流程仍由原财务办理。


## v0.19：站内消息中心

新增消息中心及导航未读角标，按当前人员展示本人应处理的报销/申请、待付款任务，以及本人单据的退回、待付款、已登记付款、申请批准/驳回/关闭结果。消息从当前浏览器单据状态派生，每单只展示当前一条提示；旧记录也可能初次出现，不代表新发送。完整历史仍在单据流转记录。

支持类别、未读和关键词联合筛选，每页20条；单条标为已读、将当前全部匹配页标为已读、点击消息打开对应单据。已读按人员ID分别保存，刷新保留，切身份清空筛选；查看单据时尝试标已读，保存失败会提示但仍可查看业务。标已读不改变审批中心待办、报销/申请状态或额度。

消息标识包含单据类型、ID、当前状态、本次提交标识、节点和流转记录版本线索；不变的状态稳定复用已读标记，进入新节点或退回重提后是新未读。过期待办不留在本页，不构建独立的消息投递日志。按具名快照确定当前处理人，旧单仅按原角色匹配，不猜人员和时间。

已读状态随完整备份保存；新备份恢复时恢复已读，旧备份缺少已读字段则保留当前已读。格式错误拒绝导入且不覆盖原存储。已读损坏时显示未知、禁标记，保留原始值；申请存储损坏时明确只显示可读取报销消息、总数不代表完整结果。已读写入配额失败不改变原状态。每人最多1000条、总量最多20000条且序列化40万字符保护，达到上限不自动清空旧标记。

演示：林晓提交报销→赵航消息中心查看具名待办并标已读，审批中心待办仍在→从消息打开退回写“补酒店水单”→林晓看到退回提示并修改重提→赵航看到新的未读任务。再用申请批准/模拟付款结果查看员工进展提示，标已读后刷新核对。仅站内展示，不发送短信/邮件/系统通知，不在后台跨设备投递或自动催办。

此功能不是此前“AI开发任务完成后弹窗”配置，开发完成系统提醒仍未配置。没有消息服务、服务端权限、推送到达率或真实用户收益数据，身份选择仍为演示机制。
