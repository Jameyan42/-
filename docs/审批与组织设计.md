# v0.8 组织架构与审批流程设计

## 问题与范围
同为主管不代表都能处理同一笔申请。固定的“主管 → 财务”无法解释金额分级、员工汇报关系变化和历史审批的责任归属。本阶段以可演示的组织与流程联动为目标；所有人员均为虚构，角色及身份选择器不是账号认证。

组织架构回答“谁属于哪里、谁向谁汇报”；审批流程回答“某笔单据按何种规则、依次由谁处理”。两者通过提交时解析人员关联，不能用部门树代替审批树。

## 组织模型与维护
部门包含唯一标识、名称、上级部门和负责人；人员包含唯一标识、姓名、部门、直属上级、角色与在岗状态。界面提供部门树、汇报树，管理员可新增或编辑，其他角色只读。最多 50 个部门、200 人，演示初始 4 个部门（含公司根节点）、10 人。

部门必须只有一个根，部门关系及汇报关系均不允许循环或失效引用。负责人必须为本部门在岗主管/管理员；在岗员工必须归属业务部门并配置有效上级。现有姓名和部门名称不能改名或删除，以保持现有按名称关联的历史数据稳定；人员可调整上级、归属和在岗状态。人员离职等变更不得使在途审批或付款节点失去有效处理人。

新增顺序：部门 → 主管 → 设置该部门负责人 → 员工。新增部门预算默认为零并显示“未设置额度”；仍采用软预警，可由财务设置额度。

## 审批配置
报销和费用申请各有一棵可编辑流程树，共用发布版本。

- 一个互斥条件：金额严格大于阈值，且费用类型匹配；“全部”表示不限制费用类型。其余进入默认分支，金额等于阈值进入默认分支。
- 每条分支 1～4 个顺序节点：申请人的直属主管、申请人部门负责人、指定在岗主管/管理员。重复人员按第一次出现的位置合并，不重复审批；不允许自批。
- 报销分支汇合后进入指定财务审核，再由该财务人员登记模拟付款。费用申请最后一个节点通过后才成为已批准并预留额度。
- 管理员可以保存未完成草稿、试算具体申请人的路径、填写原因校验并发布。发布前检查两个流程的两条分支对所有在岗员工均有有效审批人。非管理员看到的是已发布配置。
- 试算不会产生单据或预算占用；发布一个流程时，会连同另一流程一起校验和发布，版本统一递增。

默认条件为金额 > 3000 元。林晓默认分支为赵航；条件分支为赵航 → 许明。报销再加周宁财务节点。唐宁的主管和负责人都是吴安，因此去重后只有一次业务审批。

## 运行规则和历史兼容
提交或重新提交时保存版本、申请人标识、命中分支、具体审批人员及节点进度快照。只能由当前节点同标识、同角色人员处理，后续人员不可越级。在途单据不受后续发布或汇报关系调整影响；审批详情显示人员路径及状态，流转记录包含具体姓名，操作日志也记录模拟身份。

报销存在多个业务节点时，状态仍为“待主管审批”，详情路径展示具体进度；首个业务节点通过后禁止员工自行撤回，需要审批人退回。原有金额、缺附件、重复号码风险拦截继续在财务审核执行，不因树状流程绕过。费用申请驳回、报销退回仍必填原因。

旧单据没有快照时保留原固定角色流程，不自动生成或迁移历史审批责任。已有浏览器数据不被清空；首次使用新增默认组织和流程。JSON 备份包含组织、已发布流程和各单据快照，不包含独立的未发布流程草稿。旧备份缺少组织/流程时保留当前配置，缺少申请时保留现有申请；导入后补齐缺失部门的零预算并重置流程编辑草稿为已恢复版本。导入覆盖有明确确认提示。

## 产品取舍与下一步
这一版使用树形表单与连接线，不支持拖拽画布、任意层级条件嵌套、会签/或签、转交、加签、审批代理或真实账号权限。范围收敛有利于先验证两棵树的关系、路径透明度和历史稳定性。

下一步需实际招募人员试用，观察是否理解直属上级与部门负责人、是否能找到当前处理人、是否能解释草稿与发布的差异。尚未实施真实访谈，也没有业务提升指标。若反馈支持，再考虑会签、单独流程版本、后端身份系统和组织名称标识迁移。
