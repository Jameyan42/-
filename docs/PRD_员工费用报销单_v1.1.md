# 员工费用报销单产品需求文档（PRD v1.1）

**项目名称：** 轻量化智能费用报销系统  
**模块名称：** 员工费用报销单  
**文档版本：** V1.1  
**更新日期：** 2026-11-06  
**文档状态：** 产品需求基线，待与现有代码核对  
**目标客户：** 10–50 人中国大陆小型企业  
**目标用户：** 企业员工、部门主管、财务人员、系统管理员

---

# 一、项目背景与目标

## 1.1 项目背景

本项目计划开发一套真正可以提供给小型企业使用的轻量化费用报销系统。

系统的核心目标不是开发演示程序，而是让企业员工可以真实完成费用报销，主管可以审批，财务人员可以审核和登记付款，并通过自动审核减少重复性工作。

系统目前已经规划以下审核模块：

- R001：住宿费超标审核
- R002：发票重复报销审核
- R003：发票金额一致性审核
- R004：发票抬头与纳税人识别号审核
- R005：费用类型与会计科目匹配
- R006：审批流程与附件完整性审核
- R007：预算控制
- R008：审核规则配置管理
- R009：AI 辅助异常审核

以上模块是否已经实际开发完成，必须根据项目现有代码确认。

本次 PRD 重点定义员工录入报销单的业务需求，并确保后续可以与已有审核模块对接。

## 1.2 产品目标

实现以下完整业务流程：

员工登录系统 → 创建报销单 → 添加费用明细 → 上传发票与附件 → 保存或提交 → 主管审批 → 财务审核 → 付款登记 → 历史记录查询。

第一版要求：

1. 员工可以独立完成报销单填写和提交。
2. 支持多条费用明细。
3. 支持真实发票及附件上传。
4. 报销单与发票数据能够长期保存。
5. 不同员工之间有严格的数据访问权限。
6. 报销单可以进入真实的审批流程。
7. 审核模块能够使用统一的报销数据。
8. 已提交单据有可追溯的修改和审批记录。
9. 提供真实业务操作，而非只有界面效果的模拟功能。

## 1.3 本期产品边界

第一版主要支持：

- 单家企业使用
- 人民币报销
- 员工本人报销
- 员工本人收款
- 一个报销单对应一个主要报销类型
- 一个报销单包含多条费用明细
- 主管审批和财务审核
- 财务线下付款后的付款状态登记

第一版暂不开发：

- 多家客户企业共用的 SaaS 租户平台
- 复杂跨法人结算
- 多币种自动折算
- 员工代其他员工报销
- 第三方供应商收款
- 银行自动转账
- 自动生成正式会计凭证
- 完整电子会计档案系统
- 完整的商旅预订系统
- 复杂可视化审批树编辑器

不在本期范围内的功能，应保留未来扩展的合理空间，但不能为了扩展性过度设计。

# 二、报销类型设计

## 2.1 主报销类型

员工创建报销单时，必须选择以下五种主要报销类型之一。

| 编码 | 报销类型 | 业务说明 |
|---|---|---|
| TRAVEL | 差旅费 | 因公出差产生的住宿、交通等费用 |
| ENTERTAINMENT | 业务招待费 | 因正常业务活动发生的客户招待等费用 |
| OFFICE | 办公费 | 日常办公用品、耗材等费用 |
| LOCAL_TRANSPORT | 日常交通费 | 非出差场景下的公务交通费用 |
| OTHER | 其他费用 | 暂时无法归入以上类别的合理业务费用 |

## 2.2 核心业务规则

**一张报销单只能选择一个主要报销类型。**

例如：

一张差旅报销单可以包括：

- 酒店住宿费
- 高铁票
- 出租车费
- 机票

但不能在这张差旅报销单中另外添加一条办公用品采购费。

如果员工既要报销出差费用，又要报销办公用品，应创建两张不同的报销单。

## 2.3 费用子类型

### 差旅费

支持：

- 住宿费
- 机票
- 高铁/火车票
- 出租车/网约车
- 其他差旅交通
- 其他差旅费用

### 业务招待费

支持：

- 客户餐饮
- 商务接待
- 其他业务招待

### 办公费

支持：

- 办公用品
- 打印及耗材
- 其他日常办公支出

### 日常交通费

支持：

- 出租车/网约车
- 公共交通
- 停车费
- 其他市内交通

### 其他费用

支持：

- 其他费用

员工选择其他费用时，必须填写具体费用名称和用途。

其他费用不得成为绕过正常报销制度的手段。财务审核时应确认其真实费用分类。

# 三、员工录单页面总体设计

## 3.1 页面名称

**新建费用报销单**

## 3.2 页面形式

建议采用单页面分区录入。

员工可以从上到下完成信息填写，不必在多个独立页面之间反复跳转。

页面分为六个模块：

1. 报销人及所属信息
2. 报销基本信息
3. 费用明细
4. 发票与附件
5. 收款信息
6. 审批流程预览

页面底部固定展示：

- 报销金额合计
- 保存草稿
- 提交报销

## 3.3 交互原则

1. 尽量自动带出已有员工信息。
2. 只要求员工填写其能够理解的业务信息。
3. 根据费用类型动态显示字段。
4. 自动计算金额，不让员工重复填写合计。
5. 尽量减少相同信息的重复录入。
6. 允许保存未填写完成的草稿。
7. 提交前清楚提示需要补充的字段。
8. 不要求员工填写会计科目、借贷方向等专业财务信息。
9. 所有正式业务数据保存到服务端数据库。
10. 页面刷新、重新登录、使用其他设备时，已保存数据仍然存在。

# 四、模块一：报销人及所属信息

## 4.1 功能说明

员工登录系统后，自动显示其基本组织信息。

普通员工原则上不能随意修改自己的所属公司和部门。

## 4.2 字段字典

| 字段 | 类型 | 是否必填 | 录入方式 |
|---|---|---|---|
| 报销人 ID | 系统标识 | 是 | 登录信息自动获取 |
| 报销人姓名 | 文本 | 是 | 自动带出，只读 |
| 员工编号 | 文本 | 后台必存 | 自动带出 |
| 所属公司 | 组织标识 | 是 | 自动带出 |
| 所属部门 | 组织标识 | 是 | 自动带出 |
| 费用承担部门 | 组织标识 | 是 | 默认所属部门 |
| 直属主管 | 用户标识 | 提交时必须确定 | 系统匹配 |
| 员工职级 | 主数据字段 | 条件必填 | 系统带出 |

## 4.3 业务规则

### 规则 1：报销人自动识别

系统根据登录账号确定报销人。

不得允许员工通过修改网页请求来冒用其他员工身份创建报销单。

### 规则 2：所属公司与部门

默认从员工主数据带出。

普通员工不能直接修改所属法人。

### 规则 3：费用承担部门

默认与员工所属部门一致。

如果业务上需要把费用归属到其他部门，应由有权限的人员进行调整，并记录调整原因及授权依据。

### 规则 4：主管识别

根据员工组织关系自动确定主管。

如果没有配置必要的审批人，应阻止正式提交，并提示联系管理员处理。

### 规则 5：职级信息

如果住宿标准等审核规则依赖员工职级，应从员工主数据读取。

如果无法确定适用标准，审核结果应标记为信息不足或需人工核实，不得直接假定员工符合标准。

# 五、模块二：报销基本信息

## 5.1 功能说明

用于记录报销单整体信息。

## 5.2 字段字典

| 字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| 报销单 ID | 系统标识 | 是 | 系统生成 |
| 报销单编号 | 文本 | 是 | 首次保存生成 |
| 报销类型 | 枚举 | 是 | 五选一 |
| 报销事由 | 多行文本 | 是 | 说明本次报销的业务目的 |
| 报销总金额 | 精确金额 | 是 | 自动汇总 |
| 币种 | 枚举 | 是 | 第一版固定 CNY |
| 创建时间 | 时间 | 是 | 服务端记录 |
| 提交时间 | 时间 | 提交后必填 | 服务端记录 |
| 最后修改时间 | 时间 | 是 | 服务端记录 |
| 报销单版本 | 整数 | 是 | 系统维护 |
| 报销状态 | 枚举 | 是 | 系统维护 |

## 5.3 业务规则

### 规则 1：报销单编号

报销单编号由系统生成，员工不能手动输入。

编号必须唯一。

可以使用类似：

EXP-202611-0001

的编号格式，但应由系统统一管理。

### 规则 2：报销事由

报销事由为必填字段。

例如：

- 深圳出差拜访客户
- 购买部门办公用品
- 客户商务接待
- 前往供应商现场的市内交通

不能只输入空格。

### 规则 3：报销总金额

报销总金额由全部费用明细中的申请报销金额自动汇总。

员工不能直接修改总金额。

计算规则：

报销总金额 = 所有费用明细申请报销金额之和。

金额应采用精确十进制或以分为单位的整数处理，避免浮点精度问题。

### 规则 4：币种

第一版仅支持人民币。

不能简单增加美元选项但不设计汇率折算规则。

# 六、模块三：费用明细

## 6.1 功能说明

员工可以在一张报销单内添加多条费用明细。

每条明细拥有独立的：

- 费用类型
- 发生日期
- 金额
- 业务说明
- 专用业务字段
- 发票关联关系

## 6.2 通用字段字典

| 字段 | 类型 | 是否必填 |
|---|---|---|
| 明细 ID | 系统标识 | 是 |
| 报销单 ID | 系统关联 | 是 |
| 费用子类型 | 枚举 | 是 |
| 费用发生日期 | 日期 | 是 |
| 申请报销金额 | 精确金额 | 是 |
| 费用用途说明 | 文本 | 条件必填 |
| 费用承担部门 | 组织标识 | 默认继承表头 |
| 关联发票 | 关联记录 | 根据制度 |
| 部分报销原因 | 文本 | 条件必填 |

## 6.3 明细操作

支持：

1. 添加费用明细。
2. 修改费用明细。
3. 删除费用明细。
4. 添加多条同类型明细。
5. 添加多条不同子类型明细。
6. 自动汇总金额。
7. 为每条明细关联发票。

例如，一张差旅报销单：

| 明细 | 费用类型 | 金额 |
|---|---|---:|
| 1 | 住宿费 | 800 元 |
| 2 | 高铁票 | 450 元 |
| 3 | 出租车费 | 60 元 |
| 合计 | | 1,310 元 |

系统自动计算 1,310 元。

## 6.4 差旅费动态表单

选择差旅费后，出现出差信息区域。

### 出差信息

| 字段 | 是否必填 |
|---|---|
| 出差事由 | 是 |
| 出差开始日期 | 是 |
| 出差结束日期 | 是 |
| 出差目的地 | 是 |
| 出差审批单关联 | 按公司制度 |
| 出差人员 | 默认本人 |

出差信息在报销单层级填写一次。

不同费用明细不需要重复填写同一出差事由。

### 住宿费专用字段

| 字段 | 是否必填 |
|---|---|
| 住宿城市 | 是 |
| 酒店名称 | 是 |
| 入住日期 | 是 |
| 退房日期 | 是 |
| 住宿晚数 | 自动计算 |
| 申请报销金额 | 是 |

住宿晚数 = 退房日期与入住日期的日期差。

退房日期必须晚于入住日期。

跨月住宿允许录入。

住宿城市必须记录在具体住宿明细上，以便多城市出差时分别匹配标准。

### 机票专用字段

- 出发地
- 目的地
- 航班日期
- 航班号（适用时）
- 申请报销金额

### 高铁/火车票专用字段

- 出发站
- 到达站
- 乘车日期
- 车次（适用时）
- 申请报销金额

### 出租车/网约车专用字段

- 出行日期
- 起点
- 终点
- 出行事由
- 申请报销金额

### 其他差旅费用

- 费用名称
- 发生日期
- 用途说明
- 申请报销金额

第一版暂不支持自动计算出差津贴及复杂多人住宿分摊。

## 6.5 业务招待费动态表单

| 字段 | 是否必填 |
|---|---|
| 招待日期 | 是 |
| 招待类型 | 是 |
| 招待事由 | 是 |
| 招待对象或客户公司 | 按制度 |
| 参与人数 | 按制度 |
| 申请报销金额 | 是 |

如果公司配置了单次金额或人均招待标准，应使用这些字段进行审核。

不应默认要求录入所有参与人员的完整个人资料。

## 6.6 办公费动态表单

| 字段 | 是否必填 |
|---|---|
| 购买日期 | 是 |
| 物品或用途名称 | 是 |
| 数量 | 适用时 |
| 单价 | 适用时 |
| 申请报销金额 | 是 |
| 使用部门 | 默认费用承担部门 |

对于可能属于固定资产、低值易耗品或需要采购验收的支出，财务审核时应进行进一步分类。

员工选择办公费，不代表会计核算上一定直接计入办公费科目。

## 6.7 日常交通费动态表单

| 字段 | 是否必填 |
|---|---|
| 交通日期 | 是 |
| 交通方式 | 是 |
| 起点 | 适用时 |
| 终点 | 适用时 |
| 出行事由 | 是 |
| 申请报销金额 | 是 |

因公出差期间的交通原则上归入差旅费。

非出差场景下的日常公务交通归入日常交通费。

## 6.8 其他费用动态表单

| 字段 | 是否必填 |
|---|---|
| 费用名称 | 是 |
| 费用发生日期 | 是 |
| 费用用途说明 | 是 |
| 申请报销金额 | 是 |
| 附件 | 根据制度 |

其他费用默认进入需要财务确认分类的审核流程，不能自动绕开既有费用政策。

## 6.9 切换主报销类型

如果员工已经填写费用明细，再修改主报销类型：

1. 系统提示现有明细可能不兼容。
2. 不能自动将住宿费转换为办公费。
3. 员工可以取消切换。
4. 确认切换后，系统清理不兼容的明细字段。
5. 已上传的附件暂时保留，但需要重新关联。
6. 不得在未经确认的情况下丢失重要数据。

# 七、模块四：发票与附件

## 7.1 功能目标

支持员工上传真实发票，录入必要发票信息，并将发票关联到对应费用明细。

本模块必须使用真实文件存储，而不只是显示上传后的文件名称。

## 7.2 支持的文件类型

第一版支持：

- PDF
- JPG
- PNG
- XML 电子发票原始文件
- OFD 电子发票原始文件

如果某种格式无法在浏览器直接预览，应保留原始文件，并支持授权用户下载。

上传时校验文件格式、大小和内容类型，按安全策略处理不可信文件。

## 7.3 发票字段字典

| 字段 | 类型 | 要求 |
|---|---|---|
| 发票 ID | 系统标识 | 必填 |
| 发票类型 | 枚举 | 发票类记录必填 |
| 发票代码 | 文本 | 按票种适用 |
| 发票号码 | 文本 | 按票种适用 |
| 开票日期 | 日期 | 按票种适用 |
| 发票金额 | 精确金额 | 能确定时必填 |
| 购买方名称 | 文本 | 按票种适用 |
| 购买方纳税人识别号 | 文本 | 按票种适用 |
| 销售方名称 | 文本 | 可选或识别 |
| 原始附件 | 文件关联 | 有文件时必存 |
| 文件哈希 | 文本 | 系统计算 |
| 发票识别状态 | 枚举 | 系统维护 |
| 发票查验状态 | 枚举 | 有真实查验结果时更新 |

发票唯一标识必须根据票种设计，不能假设所有发票都只需使用同一种号码字段。

## 7.4 上传交互

员工点击“添加发票”。

支持：

1. 选择文件。
2. 上传文件。
3. 查看上传结果。
4. 录入或修改发票信息。
5. 将发票关联到费用明细。
6. 删除错误上传的附件关联。
7. 查看或下载原始文件。

如果系统已经具备 OCR 能力，可尝试自动识别。

如果没有 OCR，应允许人工填写。

不得将“OCR 识别成功”等同于“发票已经通过税务查验”。

## 7.5 发票与费用明细关联

一张报销单允许多张发票。

一条费用明细也可以由多张发票支持。

一张发票可以按规则分摊至同一报销单内的多条费用明细。

必须记录：

- 发票 ID
- 费用明细 ID
- 本次分摊的发票金额

同一张发票在同一报销单内被关联多次时，不能将其票面金额重复累计。

分摊金额合计不能超过该发票可用金额。

第一版不主动开放复杂的跨报销单发票余额重复使用功能。

## 7.6 发票金额与报销金额

支持以下场景。

### 场景 A：金额相等

发票金额 800 元。

申请报销金额 800 元。

金额匹配。

### 场景 B：部分报销

发票金额 1,000 元。

申请报销金额 800 元。

系统不得直接判断错误。

应允许记录部分报销原因，并按照公司政策判断是否需要人工复核。

### 场景 C：申请金额超过发票支持金额

发票金额 800 元。

申请报销金额 1,000 元。

系统应提示发票支持金额不足。

如果公司制度允许部分费用无票报销，应提供独立的政策判断，而不是直接放行。

## 7.7 发票重复报销

发票重复检测应检查已存在的有效报销记录。

需要结合：

- 发票唯一标识
- 历史报销单
- 报销单状态
- 发票使用或占用金额
- 当前单据及其版本

基本要求：

1. 已在有效审批流程中使用的发票，应防止被其他独立报销单重复占用。
2. 已批准或已完成报销的发票，应防止超出允许金额再次使用。
3. 原报销单被退回后重新提交，不应被判断为与自身重复。
4. 正式关闭、未报销的单据，应根据业务规则释放相应占用。
5. 发票本身被确认无效时，不能因为原单被驳回就自动允许再次使用。
6. 同一张发票在集团或企业的共享查重范围内不得因为不同员工提交而逃避检测。

查重应在服务端执行，并处理同时提交导致的并发风险。

# 八、模块五：收款信息

## 8.1 功能目标

员工报销时选择自己的有效收款账户。

## 8.2 字段字典

| 字段 | 类型 | 要求 |
|---|---|---|
| 收款账户 ID | 系统关联 | 必填 |
| 收款人姓名 | 自动带出 | 必填 |
| 银行名称 | 自动带出 | 必填 |
| 银行卡尾四位 | 脱敏展示 | 必填 |
| 账户验证状态 | 系统维护 | 必须有效 |

## 8.3 业务规则

第一版默认：

- 员工本人报销。
- 员工本人收款。
- 不支持第三方收款。
- 不在每张报销单内重新录入完整银行卡号。

员工可以在个人账户管理页面维护收款账户。

修改收款账户需要经过适当验证。

收款账户的敏感信息必须受到权限保护，不得在普通业务日志中明文暴露。

正式提交时必须确认所选账户有效。

已提交报销单的收款账户变更，应走受控流程并保留变更记录。

# 九、模块六：审批流程预览

## 9.1 功能目标

员工提交前，可以看到当前报销单预计需要经过哪些审批节点。

## 9.2 第一版审批流程

默认流程：

员工提交 → 直属主管审批 → 财务审核 → 待付款 → 已付款。

复杂审批制度后续扩展。

## 9.3 字段

| 字段 | 说明 |
|---|---|
| 审批流程 ID | 系统关联 |
| 审批规则版本 | 系统记录 |
| 主管审批节点 | 自动匹配 |
| 财务审批节点 | 系统配置 |
| 额外审批节点 | 适用时生成 |
| 当前审批状态 | 系统维护 |

## 9.4 业务规则

1. 员工只能查看或预览审批流程。
2. 不允许普通员工随意删除必要审批节点。
3. 提交时由服务端重新确认实际审批路径。
4. 若审批人缺失，应阻止提交并提供明确提示。
5. 如果主管与报销人是同一人，应按管理员配置的替代审批机制处理，不允许自动自批。
6. 审批流程应记录适用规则版本，防止后续配置变化使历史审批无法解释。

# 十、报销单保存与提交

## 10.1 保存草稿

员工可以随时点击“保存草稿”。

草稿允许：

- 未完成费用明细
- 未填写金额
- 未上传发票
- 未选择收款账户
- 未完成报销事由

但已经填写的数据仍需符合基础格式限制。

保存成功后：

- 数据写入服务端数据库。
- 附件保存成功。
- 返回报销单编号。
- 页面显示成功状态。

不能只在前端显示“已保存”，而服务端没有保存成功。

## 10.2 正式提交校验

点击“提交报销”时，系统必须检查：

### 报销人信息

- 已识别当前员工。
- 所属公司有效。
- 所属部门有效。
- 必要审批人存在。

### 报销基本信息

- 已选择主报销类型。
- 已填写有效报销事由。
- 币种符合当前支持范围。

### 费用明细

- 至少存在一条有效明细。
- 每条明细的子类型属于当前主类型。
- 必填业务字段完整。
- 金额大于零。
- 日期逻辑正确。
- 明细金额合计与表头合计一致。

### 发票与附件

- 满足当前费用类型适用的附件要求。
- 上传操作已实际完成。
- 需要人工录入的发票字段已按政策填写。
- 发票与明细的分摊关系有效。
- 同一张发票不能被重复计入超过允许额度。

### 收款信息

- 选择了有效本人账户。
- 账户不存在已知失效状态。

### 系统状态

- 单据当前允许提交。
- 当前提交版本有效。
- 未发生并发编辑覆盖。
- 同一次提交操作不会重复生成审批任务。

## 10.3 阻止提交与审核提示的区别

必须区分两类问题。

### A. 必须阻止提交

例如：

- 没有费用明细。
- 金额非法。
- 必填字段缺失。
- 附件没有上传成功。
- 无法确定必要审批人。
- 收款账户无效。
- 提交请求重复或数据版本冲突。

### B. 可以提交，但应交由审核处理

例如：

- 住宿费超过标准。
- 部分报销需要说明。
- 费用科目需要财务确认。
- 费用超过预算，需要特殊审批。
- 其他需要人工判断的业务异常。

是否允许带异常提交，应依据企业费用制度配置。

不能为了让员工顺利提交就默认放行所有异常，也不能把所有需要人工复核的情况一律拦截在录单页面。

## 10.4 提交成功后的处理

提交成功后：

1. 锁定当前提交版本。
2. 记录提交时间及提交人。
3. 保存适用审批政策版本。
4. 创建下一审批节点的待办任务。
5. 更新报销单状态。
6. 根据适用规则处理发票占用及预算预占。
7. 返回提交结果及单据编号。

以上相关业务操作必须具备适当的事务控制。

不得出现报销单显示提交成功，但没有生成审批任务的情况。

# 十一、报销单状态流转

## 11.1 状态定义

| 编码 | 中文名称 | 含义 |
|---|---|---|
| DRAFT | 草稿 | 员工尚未正式提交 |
| PENDING_MANAGER | 待主管审批 | 等待主管处理 |
| RETURNED | 退回修改 | 员工可以修改后重新提交 |
| PENDING_FINANCE | 待财务审核 | 主管已批准 |
| REJECTED | 已驳回 | 当前申请终止 |
| PENDING_PAYMENT | 待付款 | 财务审核已通过 |
| PAID | 已付款 | 财务已完成实际付款并登记 |
| CANCELED | 已撤销 | 按规则撤销的单据 |

## 11.2 状态转换

| 当前状态 | 操作 | 新状态 |
|---|---|---|
| DRAFT | 保存 | DRAFT |
| DRAFT | 正式提交 | PENDING_MANAGER |
| PENDING_MANAGER | 主管通过 | PENDING_FINANCE |
| PENDING_MANAGER | 主管退回 | RETURNED |
| PENDING_MANAGER | 主管驳回 | REJECTED |
| PENDING_MANAGER | 员工撤销（条件允许） | CANCELED |
| RETURNED | 修改保存 | RETURNED |
| RETURNED | 重新提交 | PENDING_MANAGER |
| PENDING_FINANCE | 财务通过 | PENDING_PAYMENT |
| PENDING_FINANCE | 财务退回 | RETURNED |
| PENDING_FINANCE | 财务驳回 | REJECTED |
| PENDING_PAYMENT | 财务登记实际付款完成 | PAID |

## 11.3 状态控制规则

1. 已提交的单据不能被员工随意编辑。
2. 退回修改后，允许员工修改必要字段。
3. 退回重提应增加报销单版本。
4. 关键业务字段发生变化，相关旧审核结果应失效。
5. 财务退回后重新提交，第一版默认重新经过主管审批。
6. 已驳回单据原则上不得直接恢复审批，应创建新申请。
7. 已付款单据不能由普通员工修改。
8. 付款失败、部分付款和付款冲销应由独立付款模块后续定义，不能通过普通编辑伪造完成状态。
9. 所有状态转换均需服务端权限验证。
10. 状态变更必须保存操作人、时间、操作类型和必要备注。

# 十二、与现有审核模块 R001–R009 的衔接

## 12.1 基本原则

所有审核规则必须读取同一套报销业务数据。

不得为了每个审核模块重新创建独立的报销单模型。

## 12.2 统一核心数据对象

至少包含：

- 员工
- 部门
- 公司
- 报销单
- 费用明细
- 发票
- 附件
- 发票与费用明细关联
- 审批记录
- 审核结果
- 适用制度及规则版本
- 付款记录
- 操作日志

## 12.3 R001：住宿费超标审核

读取：

- 员工职级
- 住宿城市
- 入住日期
- 退房日期
- 住宿晚数
- 申请报销金额
- 公司适用住宿标准

计算是否超过制度允许金额。

仅对住宿费明细执行。

不能对整张差旅报销单的全部金额直接使用住宿标准。

## 12.4 R002：发票重复报销审核

读取：

- 发票唯一标识
- 发票金额
- 当前报销单 ID
- 当前单据版本
- 历史报销记录
- 历史报销状态
- 发票金额占用关系

避免：

- 原单重提被判断为自身重复。
- 同一发票在并发提交时被重复占用。
- 历史驳回记录错误地永久占用发票。
- 发票无效状态被错误解除。

## 12.5 R003：发票金额一致性审核

读取：

- 费用明细申请金额
- 发票金额
- 发票分摊金额
- 部分报销原因
- 是否有政策允许的无票金额

区分：

- 金额一致
- 合理部分报销
- 票据支持金额不足
- 信息不足

## 12.6 R004：发票抬头与税号审核

读取：

- 当前报销所属法人
- 发票购买方名称
- 购买方纳税人识别号
- 发票类型
- 企业名称历史及允许的别名

不同票种适用不同字段要求。

不能将税号字段为空一律视为违规。

## 12.7 R005：费用类型与会计科目匹配

读取：

- 主报销类型
- 费用子类型
- 费用用途
- 所属公司
- 费用承担部门

员工录单页面不要求直接填写会计科目。

财务审核时由系统推荐或校验核算科目，再由有权限的财务人员确认。

## 12.8 R006：审批与附件完整性审核

读取：

- 报销金额
- 报销类型
- 员工组织关系
- 审批流程
- 审批历史
- 必要附件
- 文件上传状态

应区分：

- 审批尚未进行
- 审批节点被违规跳过
- 审批被驳回
- 必要附件缺失

不能将尚未轮到的审批节点误判为已经违规缺失。

## 12.9 R007：预算控制

读取：

- 所属公司
- 费用承担部门
- 费用类型
- 金额
- 费用发生期间
- 报销单状态

预算查询和正式预算占用必须分开。

不得因多次预览或重复审核而重复占用预算。

退回、撤销、驳回和已批准后的处理，应按预算状态规则执行。

## 12.10 R008：审核规则配置管理

读取适用规则：

- 规则版本
- 适用费用类型
- 适用组织
- 生效日期
- 审核参数

员工录单页面可读取必要字段要求和制度提示，但不得允许普通员工修改审核规则。

已经提交的历史单据应保存适用的规则版本。

## 12.11 R009：AI 辅助异常审核

读取：

- 费用用途说明
- 费用明细
- 发票信息
- 已有确定性规则结果
- 授权允许使用的其他资料

AI 只能提供辅助风险判断、证据和复核建议。

AI 不得绕过必要审批，也不得未经授权直接批准报销或付款。

未接入真实模型时，不得把模拟输出显示成真实 AI 分析结果。

# 十三、非功能性要求

## 13.1 数据可靠性

- 报销单保存在服务端数据库。
- 文件保存在受控存储。
- 数据库记录与文件关联关系有效。
- 保存失败时给出明确提示。
- 不得静默丢失已保存数据。
- 必须支持数据备份与恢复。

## 13.2 权限控制

至少支持：

- 员工
- 主管
- 财务
- 管理员

权限要求：

- 员工只能查看自己有权限的报销单。
- 主管只能查看有权审批的单据。
- 财务按授权范围访问业务资料。
- 管理员按职责管理组织和系统配置。

全部关键权限必须在服务端验证。

## 13.3 附件安全

- 附件不能通过公开静态链接被任意下载。
- 有权限的人员才可以查看。
- 保留原始电子发票文件。
- 校验文件类型、大小及安全性。
- 记录必要的上传和更改行为。

## 13.4 操作可追溯

记录：

- 创建人
- 提交人
- 审批人
- 财务审核人
- 状态变更
- 金额变更
- 关键附件变更
- 收款账户变更
- 操作时间

不能通过普通编辑直接覆盖关键审批历史。

## 13.5 用户体验

- 支持桌面浏览器使用。
- 表单布局清晰。
- 金额自动汇总。
- 错误提示定位到具体字段。
- 草稿可继续编辑。
- 上传文件时有进度及结果反馈。
- 重要操作有明确确认及完成状态。

# 十五、建议的实际使用验收流程

准备三个不同账号：

- 员工 A
- 主管 B

# 十七、正式试用前必须确认的事项

本 PRD 已经确定录单的主要产品结构，但以下制度参数需要由实际使用企业确认，不能由开发人员擅自编造：

1. 各类费用是否必须提供发票。
2. 允许无票报销的具体情况。
3. 住宿费及招待费标准。
4. 超标费用是否允许申请特殊审批。
5. 部分报销的具体规则。
6. 各费用类别的审批权限。
7. 员工收款账户的验证方式。
8. 发票重复使用及历史单据处理规则。
9. 电子凭证的保存、查验与归档责任。
10. 单据撤销、驳回、退回后重新提交的具体规则。

在上述制度未确认之前，系统可以完成开发和受控试用，但不得自行声称已经符合某家公司的全部费用管理制度。

# 十八、最终产品要求

本系统的第一目标是：

**让一家 10–50 人的小公司真正使用这套产品完成日常费用报销。**

员工能够：

- 创建报销单
- 添加多条费用明细
- 上传发票
- 保存草稿
- 提交审批
- 查看状态

主管能够：

- 查看待审批单据
- 审批通过
- 退回修改
- 驳回

财务能够：

- 查看报销单和发票
- 使用自动审核辅助判断
- 处理异常
- 确认财务审核
- 登记付款
- 查询和导出报销记录

未来在基本业务稳定的基础上，再逐步增强：

- 自动发票识别
- 费用规则配置
- 智能异常分流
- AI 辅助审核
- 更复杂的审批规则
- 预算控制
- 会计凭证生成

**产品开发顺序应由真实业务价值、用户使用体验和系统可靠性决定，而不是由功能数量决定。**
