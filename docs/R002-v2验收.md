## 2. 需求核对与产品判断

| 需求 | 交付与边界 |
|---|---|
| 发票与单据字段 | 全部要求字段、五类型、姓名/部门、唯一记录号、独立自动及人工状态，单票单单 |
| 五笔种子 | BX-H001–H005单独存放，金额/类型/日期/销售方明确，首次保存后刷新不覆盖 |
| 精确策略 | R002-01同类型代码＋号码；R002-02双方无代码数电同号 |
| 潜在冲突 | R002-03跨类型同号/代码不对称；不直接认定违规 |
| 传统缺代码/其他缺可靠标识 | 前者待补充且不查重；后者人工核查 |
| 金额和日期 | 安全整数分，保留原输入；拒绝负数/三位小数/科学计数法/越界，0元人工；公历有效日期 |
| 历史状态 | 已通过、审核中、已驳回、已撤回均人工，展示具体依据，不自动豁免 |
| 多命中、自身排除 | 返回全部；只按当前单号排除自身，其他单号引用相同发票仍命中 |
| 四页 | 发票录入、自动结果、人工复核、历史库；中文、沿用现有视觉、移动布局 |
| 历史管理 | 号码/代码/单号/姓名搜索、状态筛选、新增/编辑、恢复初始化历史库 |
| 独立人工结论 | 人员和原因必填，时间保存，一版本只能一次，原自动证据保留 |
| 重审及快照 | 单号/提交时间/发票记录号不变，追加版本，旧版本只读；最新待复核可处理 |
| 保存前本地复查 | 读取最新本地数据后执行查重再保存，写前旧值冲突保护；不声称跨用户事务 |
| 恢复 | 明确二次确认，只替换库，不清R001或R002单据/证据/复核；损坏证据拒绝恢复 |
| 纯函数/类型/隔离 | 时间调用方传入，规则无存储和随机数，不改输入；独立键及严格类型 |
| 文档与测试 | README、CHANGELOG v2保留历史，T01–T30＋额外完整性用例、存储/复核及端到端实际执行 |

自动审核用于**识别风险**，不能替财务认定违规。匹配不以金额或人员为键，因此跨员工/金额修改仍能命中。R002通过不等于整单通过：无人工结论的新审核业务状态仍“审核中”。人工通过/驳回另存，界面同时展示当前业务状态与所选版本的自动/人工结论。

证据快照保存所有同号码候选（包含同类型不同代码未命中的候选），记录来源/比较/排除自身计数、数据版本、规则版本、时间和当前输入；不会为每次审核复制无关票据全集。历史库编辑后可以重审，新旧版本分别反映当时依据。本地JSON校验不等于防篡改审计。

为避免同单修改票面让旧身份悄悄消失，第一笔可靠票面一经绑定，类型/代码/号码只读，更换发票新建单据；可补正其他资料后同单再审。资料不足的早期版本允许补齐。最新版本数据错误时，最近的有效版本仍在查重历史中，库页标出有效版本号；不让错误输入“洗掉”此前有效发票。

已实现用户要求；明确不做税务验真、OCR、AI、ERP、银行、多票合并或R003。没有实时跨企业/跨浏览器/跨账号去重、权限认证或真实试点收益。仅中国境内人民币模拟，当前库＋本地R002有效单据，不自动联查R001和旧轻报票据台账。提供的BX-H004为21位字符串原样保留，另测试20位含前导零，不擅自修正种子。

## 3. 数据、保存及失败保护

`qingbao-r002-v1`包含schema=1、revision、library和documents；每笔document包含audits，audit包含inputSnapshot、automatic和独立humanReview。R001仍使用`qingbao-r001-v1`，没有迁移或清空操作。

初次没有键时只在内存提供种子，第一次成功写操作持久化；再次载入只读现存内容，不补回或重置被修改的历史。恢复按钮经确认仅重置library，保留documents及全部版本。坏JSON或损坏单据不能安全恢复时停止写入并保留原值；仅库损坏而单据完整时允许恢复库。

模拟库最多200条、R002单据200笔、每单20个审核版本、序列化JSON不超过220万字符，浏览器可能更早用尽配额，均报错保留原值而不删除证据。写前最新读取加旧值检查降低同源旧页面覆盖风险，但不是数据库原子事务/跨用户实时一致性。不使用生产资料。
