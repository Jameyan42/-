# OCR 辅助录入：设计与验证

## 用户问题与范围
假设员工反复填写金额和长号码容易出错。通过图片 OCR 降低输入负担，同时保留人工核对。支持 PNG、JPEG、WebP，最多 6 MB / 1600 万像素；识别前可左右旋转 90°，每侧按旋转后坐标裁去 0～40%；裁剪后长边缩至不超过 2200 像素。预览采用相同变换但较小尺寸，原文件不变。v0.27增加PDF预览和逐页识别（最多20页、6 MB），详见《PDF发票识别设计》。二维码解码、全文件批量多票拆分、发票真伪和税务验真不在范围内。

## 实现与数据流
1. 浏览器读取用户选择的图片，显示临时预览；不发送图片。
2. 可先旋转或裁去无关背景，调整后旧候选失效，已有表单字段不变。
3. 同源 Worker 运行 Tesseract.js，加载英文字及简体中文 best_int 语言数据。
4. 从真实识别文本提取有标签的号码和价税合计。没有标签、号码长度不符或多个歧义金额时不猜测，候选留空。
5. 用户可修正候选；勾选已核对才能填入，空字段不覆盖原表单。
6. 员工自行补充用途并提交。直接选文件只保存字段、文件名（PDF含页码）、引擎名称及核对来源，不保存原文或置信度；明确上传至附件区并关联时才保留原件字节，完整备份含该原件。

引擎置信度只是文本识别参考，不代表发票真伪、单字段正确率或可泛化准确率。修改图片后清除旧的 OCR 核对来源。已使用 OCR 的单据详情显示“曾使用”而不承诺其字段未经后续编辑。

## 状态与异常
- 未选择 → 提示选择图片，不改变表单。
- 加载 → 显示引擎准备；语言加载后显示识别百分比，允许取消。
- 成功 → 展示原图、可编辑候选、原文与参考置信度，不自动覆盖或提交。
- 失败 → 不清空手工字段，允许换图或手工填写。
- 超过 90 秒 → 停止等待并回退。若取消发生在初始化阶段，初始化完成后立即释放 Worker；不继续应用结果。
- 关闭弹窗 → 释放临时 URL、取消当前任务；未保存的表单关闭前要求确认。

## 资源与发布
模型、Worker 和三个平台适配内核从 npm lockfile 校验的包复制，随网站一起发布，不使用外部识别 CDN。v0.27加入PDF.js、CMap/字体/解码资源后全部静态资产约21.1 MB，实际首次只选取匹配设备的内核及语言文件，约 10 MB；后续 HTTP 缓存可能复用。资源摘要位于 ocr/manifest.json，第三方声明和许可证一同保留。

普通单文件页面仍能运行基础功能；OCR 需要 HTTP/HTTPS 和同目录 ocr、samples 静态资源。本地 file:// 下显示明确提示，不禁用证书、浏览器安全或跨域检查。

## 验证范围
- 单元测试：中文/英文标签、全角、空格、千位分隔符、无标签和歧义、文件限制与元数据备份。
- 浏览器真实引擎：虚构样票识别号码 12345678901234567890 与金额 268.50；确认前保留原表单，确认后记录来源。
- 失败路径：加密/损坏/超页数PDF、坏图、取消、未保存关闭、移动端布局。
- 网络检查：识别时只有同源 GET 资源请求，没有图片 POST 上传。

单张合成样票不能代表真实票据总体效果。后续应建立包含不同版式、模糊程度、旋转、拍照与扫描图的脱敏或虚构测试集，按号码精确匹配率、金额精确匹配率、空字段率和人工修正时间分别评估。不要编造准确率。


v0.6 增补：图片编辑是对技术可用性的改进，尚无真实用户反馈证明收益。合计优先取标签本行，不混入下一行税额；同图出现冲突的号码或合计时留空。网络故障中断语言资源加载的场景已单独验证，提示后允许手工填写。


v0.27产品复盘：用户指出“能上传PDF却不能识别”，这是常见发票格式在核心录入链路上的断点。本阶段优先补齐格式覆盖，不新增独立菜单。选择逐页预览与人工确认，避免多票金额被静默合并；统一转图OCR，先复用现有字段和风险链路。代价是电子PDF未直接提取文字，识别速度和版式覆盖仍受OCR影响，后续需要真实授权的样本集再评估文本层优先及批量拆票。虚构样票通过不能作为准确率或效率收益。
