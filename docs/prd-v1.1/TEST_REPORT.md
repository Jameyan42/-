## 测试中发现并修复

- 原查详情使用optional chaining省略已失效审核字段，现明确返回null，避免前端误用旧结果。
- 原双员工抢同票夹具共用A收款账户，新本人账户检查先拒绝B；修正夹具为两个分别验证的本人账户后，竞争实际仍为1成功/1冲突。
- 仅按分摊构建原规则输入可能把“全票1000、本次800”看成完全相等；服务端适配补充全票/实际用额及独立部分原因，不修改冻结R003纯规则。
- 新建或修改若允许降级旧模型，可绕过账户/主类型必填；新建统一v2，已有v2拒绝降级，旧历史仍可读/按旧路径处理。
- 草稿原严格日期/金额和票号约束不能保存半填数据；增量nullable字段配合独立提交校验，已填非法值仍拒绝。
- TypeScript将显式泛型Buffer返回视为可能包含SharedArrayBuffer，测试PDF构造器改用真实Buffer.from返回类型推导，重新执行后端类型检查通过。
- 账户在待付款阶段停用会导致原状态无法继续，增加非本人财务确认尚未实际付款后的受控退回，完整重新审批；实际API测试覆盖失效拦截、自操作/未确认/已付款拒绝。
- 前端失败上传原状态可能停留“正在上传”；增加失败状态、无成功链接、可重试的实际浏览器验证。
