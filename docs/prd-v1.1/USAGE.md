# 员工费用报销单 v1.1 使用与升级

沿用现有业务服务，不是新的独立网站。PRD原文保持不变；冲突与保守处理见 IMPLEMENTATION.md。

## 升级与启动

1. 先按docs/s003/BACKUP_AND_MIGRATION.md做DB+原件一致备份并验证恢复目标。Git不能恢复财务数据。
2. 在测试库验证增量迁移004_employee_claim_v11.sql。迁移保留旧单/旧状态、增加员工编号和收款账户表，允许新版草稿的未填金额/日期为NULL，不改旧审核函数。
3. `.env`增加独立 `ACCOUNT_ENCRYPTION_KEY`：密码管理器生成的32字节随机密钥，以64位十六进制填写。不与SESSION_SECRET共用，不放VITE变量，不提交、不贴聊天。Compose也传入此变量。
4. 密钥必须单独加密/离线备份；DB备份只含密文。丢失密钥不能恢复完整账号，不能随意换key而不迁移旧密文。本期尚未提供在线密钥轮换工具。
5. `npm ci`、`npm run db:migrate`、`npm run build`、`npm run server`。初次空库管理员初始化继续按S003手册；现有库不能重新bootstrap。后端启动会检查004新增结构，未迁移时不继续提供半可用新业务。
6. 在运行服务的同一电脑打开PUBLIC_ORIGIN。云端127.0.0.1不是你的电脑网址；真实公网URL、HTTPS和异机验收仍需部署。GitHub Pages仍是演示。

## 公司设置和收款账户

- 管理员配置实际部门、直属主管、至少一名可处理本申请的有效财务、公司基准及已批准制度。员工编号初始沿用已有登录标识，后台持久化；不伪造HR信息。
- “公司与人员”中收款账户验证制度默认未配置。只有公司实际批准线下核对方式后，才选择“财务线下核对本人账户”并填写制度修改原因。软件不替公司决定验证制度。
- 员工进入“收款账户”，填写本人银行名称/账号并用本人当前密码确认。收款人只能从本人姓名带出；新记录是待验证，不自动生效。替换账户用新增记录，旧原值不被覆盖。
- 财务在同一收款页查看待核对队列，通过企业认可的渠道实际核实姓名、完整账户及归属后，填写依据、勾选确认，系统记录为“已线下核对”。这不是银行实名认证或银行接口验证。
- 普通查询、审批详情、CSV和操作日志不自动返回完整账号。非本人财务在待付款单里因线下付款需要，可以填写原因查看完整快照账号，服务器鉴权/留痕，页面60秒后隐藏。不要把完整账号写在意见或截图中。
- 员工可以停用自己的账户；待付款登记会重新检查快照账户仍有效，停用可能阻止登记。已提交单不能直接换账户，需退回修改重提；待付款阶段由非本人财务明确确认尚未实际线下付款并填写原因，使用“退回修改收款资料”，重提需完整重新审批，已登记付款不可退回。历史已付单不补造账户。

## 差旅1250元示例（只用虚构资料联调）

1. 员工点“新建报销单”，主类型改为差旅费，确认类型切换提示。
2. 填报销事由与整单出差信息；添加800元住宿（城市、酒店、入住/退房、发生日），再添加450元高铁（出发站、到达站、乘车日、用途）。合计显示1250.00元。
3. 可先保存不完整草稿，空金额保持空，不伪造为0；保存后有唯一单号。
4. 上传对应PDF/图片/XML/OFD原件，看到服务器确认，再填写对应票面和分摊。示例应使用金额/号码与所录值一致的虚构PDF，不使用真实员工资料。
5. 每张发票可分摊到本单多条明细，分摊总额不超过票面；本期不开放跨单余额使用。票面大于本次分摊时填写独立部分报销原因。
6. 选择本人有效收款账户，核对六区表单及审批预览，保存并提交。错误返回字段路径并标记字段；规则超标等提示和结构缺失分开。
7. 主管用自己的账号审批；财务读取同一明细、附件及原R001—R004依据。未配置住宿标准需人工核实，不会自动变为通过；票额支持不足不能普通批准。
8. 财务确认线下付款已经完成后登记1250.00元。系统没有银行转账能力；员工查已登记付款、财务导出台账、原审批/提交快照保留。

## 其他交互

- 五种主类型的子类型不混用，住宿只按住宿明细执行R001，不用整个差旅合计计算住宿标准。
- 动态字段包括住宿、飞机/火车、出租车、办公物品、招待对象/人数及其他费用名称。适用时字段不代表已经配置了所有企业额外制度。
- 切换主类型会确认并清理不兼容明细/分摊，保留票面和原文件，需重新关联；切换有专用数据的子类型也提示确认。
- 删除明细会同步移除该明细分摊并重算合计，原件保留。删除票面关联不删除原始字节。
- 其他费用需财务人工核实分类；若公司没有明确纳入金额支持政策，审核为资料不足，不能通过其他费用绕过制度。管理员在批准后可显式纳入现有票额支持政策。
- 企业可以显式启用主管处理前撤销；提交时保存制度快照。未启用、版本变化或主管先处理则拒绝；撤销与审批串行，原件和历史保留，发票释放仍取提交制度。
- 旧混合类型单据继续原编辑方式和状态编码；新建统一使用v1.1，不接受客户端用旧模型绕过新必填。旧静态演示不属于这个后端API契约。

## 边界

当前仍只支持原四票种，不自动识别所有客运票；部分票种免税号、无票制度、企业名称别名、出差申请单真实关联、企业额外招待标准/附件要求、预算、R005科目确认、AI及正式OCR接入尚待明确制度或后续开发。未提供的新能力不能标记为已通过。

本期不提供银行转账、第三方收款、账户自动实名认证、已提交单直接改收款账户、金额冲销或复杂替代审批。无主管/自批时阻止并联系管理员，不擅自创造替代人。

付款更正后的台账口径、政策并发版本检查、重置密码/主管重分配专用界面仍是原计划待办，没有用本期新表单冒充解决。正式定时/异地/加密备份、运维报警、负载、真实异机及企业验收亦未完成。

## 回退边界

Git基线153c978保留了本次开发前的原始PRD与旧实现。004不删除旧记录，但旧程序并不保证能读取新v2未填草稿或处理新收款逻辑，因此不能在已出现v2数据后盲目降级旧程序。

回退前先维护/停止写入，保全当前DB、原件、独立密钥和现有新单据。优先回退到仍兼容v2的版本；必须使用旧快照时，只恢复到新空库/新目录，核对新增业务差异后再按授权切换，不能覆盖唯一副本或丢弃新单。此轮隔离验证不需要对原数据库执行回退。
