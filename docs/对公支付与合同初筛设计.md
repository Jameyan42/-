# 对公支付与合同初筛（v0.20）

## 要解决的问题
员工报销的收款人通常是员工，对公支付的收款人是供应商。继续套用报销单会遗漏合同依据、收款账户和累计支付管控，因此新增独立的供应商、合同和对公单模型。目标是用虚构业务展示企业费控平台的另一条主链路，不宣称支持企业规模并发或生产财务。

## 模块与规则

### 供应商档案
管理员维护全称、虚构统一代码、同名户名、开户行与 DEMO- 开头的虚构账号；代码和账号不能与其他供应商重复。可启停、维护，不提供删除。停用阻止新合同及新提交/重提对公单，已经在途的单据仍沿收款快照流转，是否支付由人工审核。主体改名/代码变化后，旧合同不能用于新付款；需新建并复核对应合同。账户变更只影响后续提交。

### 合同工作台
员工选择供应商，填写唯一编号、标题、人民币含税总额、起止日期，粘贴正文或导入UTF-8 TXT。正文最多30000字、TXT最多90 KB；不解析PDF/DOCX，不保存原合同二进制文件，也没有电子签章。

`local-contract-1` 在浏览器做确定性规则初筛：核对完整供应商名是否出现，检索交付、验收、付款、发票、违约和争议处理关键词，提示全额预付、无限责任和单方解除表述。提示展示规则ID、等级、命中原文或“未检出”、核对建议。规则不理解完整法律语义，含否定或复杂改写时可能误报漏报。未命中不代表安全，未检出不代表条款一定缺失。

财务或管理员必须阅读全文、勾选人工核对并填写1～500字意见，选择通过或要求修改。高风险处理依据由人写入意见，不自动判断意见是否充分。提交人不能自审。员工仅能修订本人待复核或需修改合同；修订版本递增，重新初筛并清除通过记录。已复核合同当前不可直接修订，需另建合同，避免改变关联付款依据。原型未实现合同作废、补充协议和履约台账。

用户已选择先做本地规则审查，真实AI稍后接入。当前AI按钮禁用，没有模型调用、密钥、费用或合同外传。后续真实AI需要后端鉴权和密钥管理、模型选择、结构化结果与原文证据校验，以及费用/数据范围确认。当前未开发模型服务端适配器，不能声称AI已接通。

### 独立对公单
员工仅可使用本人提交且已人工复核的合同，供应商必须启用且当前法律主体与合同快照一致。填写事项、金额、期望付款日期和用途，金额大于0、最多100万元、精确到分。合同总额也为人民币且最多100万元；暂不支持多币种。

须先由管理员在审批流程发布财务分工模板，包含独立财务、总账和付款人。当前复用已发布报销规则来解析业务审批分支（支付单类型固定“其他费用”），但数据和操作历史单独保存，不伪装为员工报销。尚无独立对公审批配置标签。

提交 → 业务审批节点（模板为部门负责人）→ 财务审核 → 总账复核（科目/核算归属必填）→ 指定付款人员模拟登记。每节点按快照具体人员与角色办理，管理员只读支付单；退回需原因。本人首节点未通过可填写原因撤回，退回/撤回后可编辑并重提。重提重新生成收款、合同版本及审批快照，保留历史。

付款需有效日期、方式、4～60字参考号和模拟确认。新对公付款与已有报销/对公已付款参考号跨业务判重；报销单笔及批量新付款同样核对对公记录，忽略首尾空白和大小写。只是本浏览器演示规则，不是银行交易幂等。付款只登记状态，不会转账或生成总账凭证；期望付款日不代表实际付款/到账日，也不自动定时支付。

### 合同额度与快照
以分计算：可用额度 = 合同总额 - 在途对公单 - 已付款对公单。退回/撤回不占用，重提再次校验；支付登记把在途转为已付，不重复占用。合同详情展示分解；页面列表与CSV遵守当前模拟人员范围。

提交时固定供应商全称、统一代码、收款户名、开户行、账号、合同版本、申请人员ID、流程版本和各节点人员。组织调整保护对公未来节点和付款责任人。该模型只支持单浏览器顺序操作，未解决服务端事务或多个标签页/多人并发占用。

## 持久化与兼容
新增 `qingbao-enterprise-v1`，schema1，供应商/合同/对公单各最多200条，单记录操作历史最多100条，整体序列化最多80万字符。保存前验证关联、规则结果、审批/总账/付款记录及合同累计额度，写入成功后才更新内存。容量失败保留表单和原业务数据；坏存储保留原始值、关闭本模块写入及完整备份，阻止无法核对的组织修改和报销付款。

完整JSON备份新增enterprise字段；旧备份没有该字段时保留当前企业业务。当前企业数据无法读取时，旧备份不能假装恢复此部分，需包含企业业务的有效备份。导入校验原有/新对公引用、部门和在途人员，和其他键一起使用现有多键回滚保存；无浏览器崩溃事务保证。恢复前确认明确说明是否替换企业业务。已有企业业务时禁用旧的一键重置，避免重置关联组织导致记录悬空；不自动删除数据。

## 范围与下一步
对公任务在独立页面办理，尚未合并原审批中心、站内消息、我已处理及报销付款工作台；这些原模块继续处理员工费用。对公合同额度未计入原部门报销预算或费用洞察。报销多附件继续可用，对公单本阶段尚无履约/发票原文件附件及自动付款条件校验。下一步优先评估对公附件和统一待办，再接真实AI；组织、费用政策和真实财务服务仍需要业务调研。
