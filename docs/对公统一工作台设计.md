# v0.24 对公统一待办、已处理与消息（2026-10-24 上海）

## 目标
让主管、财务、总账和付款人员在同一入口看到员工费用和对公支付任务，减少切换独立页面寻找单据。统一入口使用独立corporate类型，保留对公合同额度、收款快照、原件、预审及指定人员处理逻辑。

## 业务与交互
- 审批中心增加“对公支付”类型，当前可处理概览、类型数量、关键词、提交时间排序和CSV均包含对公。只汇集当前节点，处理后移出原人员，下一节点出现；不能仅按角色或部门代办。
- 从统一待办直接打开原对公详情；办理或关闭后保留当前页面及筛选。总账必填科目/核算归属，付款确认模拟并填独立参考号，原风险重算和财务拦截继续执行。对公付款任务可在统一待办办理，报销付款工作台的批量登记范围仍为报销。
- 统一待办每页20条，搜索/类型/排序/换身份时回到第一页；列表页码自动限制在有效范围。CSV导出所有匹配页，不仅当前页。概览是当前人员全部可读取待办，列表另报筛选数量，避免把筛选后数当总体。
- “我已处理”增加对公类型；仅新执行的通过/退回/付款产生operation，保留人员ID、当时角色、节点、流程版本、提交轮次、事项/金额、备注和总账或付款摘要。处理次数不等于单据数或支出额。原有日期范围、快捷日期、分页及筛选CSV复用。
- 重提后的事项/金额不覆盖旧操作；旧对公历史虽有具名文本，也不追补处理时摘要。已记录操作的原处理人可只读打开当前单据，即使重提改了路径；当前节点处理权限仍只给新指定人员。不能从姓名或同岗位猜测历史可见范围。
- 消息中心增加单据类型筛选，按当前人员提供对公审批/总账/付款待办和本人退回、待付款、已付款、撤回进展；退回展示原因，付款说明只是模拟登记。员工按createdBy认领，不按姓名猜归属。
- 每单当前一条提示，消息键使用单据类型/ID/状态/提交快照/节点/历史事件线索，三类同号互不冲突；旧报销和申请键生成保持原样。已读独立于审批，按人员保存，跨页批量只作用于全部匹配结果。新节点/重提生成新未读，旧待办不构成独立投递档案。
- 打开消息尝试标记已读；已读写入失败仍可看单据并提示。标已读绝不修改审批、合同额度或付款信息。

## 模型与兼容
对公history条目可新增operation：schema=1、kind=corporate，流程状态沿用现有对公链路。新操作时间与外层流转时间统一，验证人员/角色/备注/状态/动作一致；总账/付款摘要按对应节点保存。企业整体先校验、持久化成功再更新内存，失败不增加已处理次数。

完整备份仍为format version=1，原企业业务和消息已读存储键不改，不引入新业务数据表。备份验证新增corporate操作结构和外层一致性检查，拒绝错类型、非法流转、缺少摘要等格式；旧记录缺operation合法，已读结构兼容。旧快照、付款及原件引用不迁移。

企业或申请存储损坏时保留原始值，统一页面继续展示其他可读取集合，但提示“列表不完整”，导航角标用“?”；统一待办/已处理导出暂停，避免假完整文件。已读损坏继续使用原有未知/禁标记提示。恢复有效备份后重新计算，普通浏览不会覆盖坏存储。

## 演示验收
1. 已发布财务分工下，林晓提交对公单；主管赵航无此待办，许明能看到。许明在审批中心办理，周宁从消息办理，总账高璇和付款杜川分别在统一入口填写信息。
2. 每人处理后“我已处理”有独立对公记录，日期筛选和CSV保留科目、核算归属或付款参考号；员工看到模拟付款结果。
3. 标已读后待办仍在；从消息退回补验收材料，员工查看原因并改金额重提，主管获得新未读，旧金额仍在旧操作中。
4. 25条虚构对公待办验证20+5分页及全筛选CSV；消息对公筛选跨页已读不误标报销/申请。
5. 验证操作及已读备份往返、坏操作拒绝、配额失败重试、损坏集合提示、手机布局。具体结果见阶段验收。

## 边界
只整合对公支付任务，不含供应商变更审批、合同复核待办、预算跨类型合并或对公批量付款。站内派生提示不等于消息服务、催办、邮件短信、系统通知或AI开发任务完成弹窗。没有后台推送和跨设备同步，角色选择仍是演示机制，记录不防篡改。真实AI、官方发票验真和银行转账继续未接入。
