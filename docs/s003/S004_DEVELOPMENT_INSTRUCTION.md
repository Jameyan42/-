## 一、目标与范围

你是一名高级全栈开发工程师，同时熟悉企业报销和财务核算。

请在现有轻报单公司业务版中，实现“财务科目确认”，将已有 R005 费用类型与会计科目匹配规则接入真实后端流程。

目标是：员工提交报销后，财务能逐条确认费用对应的科目，系统检查是否符合公司配置，保存确认依据，再继续现有审批和付款登记流程。

本次只开发这一项功能。不要重建系统，不新增独立网站，不扩展预算、AI、OCR、银行支付、凭证生成或财务软件接口。

**科目匹配通过不等于已经记账，不自动生成会计凭证，不等于发票验真，也不等于已经付款。**

## 三、业务规则

### 1. 公司科目配置

- 以当前单公司为范围保存科目表和费用映射，不引入多租户。
- 科目至少包括代码、名称和启用状态。科目代码按字符串处理，保留点号及前导零。
- 映射至少包括唯一编号、费用类型、适用起止日期、允许科目、推荐科目、状态和说明。
- 推荐科目必须属于允许集合；科目引用必须存在且可用。
- 同一费用类型与日期若出现多个同优先级有效映射，应拒绝发布并指出冲突，不能随意取第一条。
- 每次修改发布产生新版本，记录操作者、时间和修改原因；使用预期版本检查，防止两名管理员相互覆盖。
- 只允许管理员维护公司配置；财务只读配置并进行单据确认。
- 正式业务库初始不导入 `defaultAccounts()` 的模拟科目或映射。缺少配置应明确提示“未配置，待维护”，不能回退到演示配置并显示通过。
- 可以提供显式标注的虚构配置文件供独立测试库使用，不自动写入正式库。
- 本期继续支持既有四种费用类型，不顺带增加新费用类型。
- 优先按业务版费用名称建立显式配置。若确需对旧规则名称做适配，使用独立、可测试的明确映射，同时在证据中保留原始名称及适配依据。

### 2. 员工与主管

- 员工填写原费用明细即可，不要求懂会计或选择科目。
- 提交前展示的推荐仅供提示，不代表已经财务确认。
- 配置缺失或员工未选科目，不得新增员工提交或主管审批的硬拦截。
- 员工、主管不能通过修改请求参数写入或伪造财务确认结果。
- 主管继续使用现有通过、退回、驳回流程，不新增节点。

### 3. 财务确认

- 仅对处于 `FINANCE_PENDING`、当前财务有权查看、且并非本人申请的单据操作。
- 每条费用明细显示费用类型、金额、说明、适用规则、推荐科目和可选科目。
- 允许财务选择允许集合中的其他有效科目；非推荐科目需填写实际业务原因。
- 每条明细必须由财务明确确认。不得仅因系统有推荐就自动填成“已确认”。
- 保存明细 ID、单据版本、费用原始字段、所选科目代码和名称、配置版本及快照、R005 原始输出、确认人、确认时间和说明。
- 必填项、配置和审核数据错误必须明确显示，不能用通用“系统异常”掩盖。
- 确认保存与最终批准是两个明确动作。批准时服务端重新验证全部确认仍有效；如果任一条未确认、过期、被规则阻断或资料不足，应阻止财务批准。
- 本期不提供任意绕过科目限制的放行按钮。未配置、配置冲突或不允许科目，应维护配置或退回处理。
- 所有非 PASS 状态均需明确处理，不能把写一句复核原因等同于完成科目确认。
- 财务仍可退回或驳回，不能因没有确认科目而禁止这些纠错操作。
- 科目确认失败不能覆盖或清除原 R001—R004 自动审核结果。

### 4. 版本、历史与启用边界

- 以费用发生日期选择有效映射，不用今天替代业务日期。
- 财务首次打开不锁定配置；第一次保存有效确认时，服务端原子保存该单据版本的科目配置快照，不能接受客户端伪造快照。
- 同一单据版本后续逐条确认使用该快照，不混用多个版本。批准时根据同一快照和当前明细重新验证。
- 公司后续发布新版本不静默更改既有确认；新进入确认的单据使用当时已发布且适用的配置。
- 需要应用新配置时，财务显式执行“按最新配置重新确认”，填写原因。原确认保留为历史，当前确认失效，全部明细重新确认。
- 单据退回后如发生修改或产生新版本，旧确认不能用于新版本批准；保留旧记录，并按新版本重新确认。
- 配置停用只影响新确认，不撤销已经固定在单据快照中的历史确认。本期不做紧急追溯撤销；不得暗中改变已通过或已付款状态。
- 必须使用持久化的服务端启用边界：启用后新提交或退回重提的单据版本要求科目确认；不能只按浏览器时间判断。
- 升级前已提交且仍在处理的单据，不得突然无法付款。明确标记“历史版本，未纳入本期科目确认”，沿用原流程；如财务显式纳入则需确认并留痕。
- 升级前已有待付款、已付款、驳回和关闭记录不得补造确认，不得更改其原状态。
- 发布前必须测试上述历史兼容路径，不能仅测试空库。

## 四、界面要求

- 沿用 `src/business/` 中真实登录业务界面，中文显示，不增加模拟切角色。
- 管理员页增加简洁科目及映射管理，至少能新增、修改、停用、校验和发布版本；不要让用户直接编辑数据库。
- 财务单据详情增加“科目确认”区，逐条展示并保存，清晰区分推荐、已确认、需重确认和错误。
- 旧自动审核依据继续可见，新增科目依据不能取代它。
- 单据详情可查历史确认、改选原因和操作者；员工与主管仅在现有单据权限内只读，不获得其他人员资料。
- 已付款单据只读，不能通过新接口改科目或改金额。
- 不在付款按钮上使用“入账”措辞。

4. 数据库外键、唯一约束保证确认关联当前公司的真实明细；服务端从数据库读取金额及单据归属。
5. 金额继续使用整数分，不把本期开发变成金额模型重构。
6. 每次写操作校验登录、角色、记录范围、当前状态、版本、CSRF；继续禁止财务审批本人单据。
7. 使用事务和行锁/乐观版本。重复点击或请求重试不得产生重复有效确认；冲突需返回明确提示。
8. 与原 `operations`、账号停用失效及备份维护锁机制兼容，不能只保护前端按钮。
9. 确认记录只追加/失效，不物理删除或静默覆盖历史；运行时数据库账号遵循原最小权限。
10. 备份/恢复必须覆盖新表及引用关系，在新空库实际验证，不能覆盖现有唯一数据库。
11. 原单据 CSV 保持原结构兼容。若提供科目明细导出，使用独立入口，一行一条费用，继续服务端权限过滤与公式注入防护，不把整单总额重复当明细金额。
12. 正式迁移前先做可验证备份。只对独立测试库写模拟数据，不迁移真实资料来“测效果”。

## 七、开发顺序

1. 复查现状并记录与本文的差异，先确认无重复实现。
2. 备份独立测试环境，设计增量迁移、版本和历史兼容策略。

4. 在原业务页面接入配置维护和逐条财务确认。
5. 接入财务批准校验，完成全流程、历史兼容与恢复验证。
6. 更新文档并给出真实结果，完成后停止，不擅自进入下一项功能。
