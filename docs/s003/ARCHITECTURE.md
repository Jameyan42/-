# S003 架构检查与改造

日期：2026-11-05。本轮交付可运行的单公司服务端版本，不能把本地测试等同真实企业上线。

## 检查到的原项目

| 范围 | 真实代码现状 | 可用于真实多人业务吗 |
| --- | --- | --- |
| 前端 | 原生JavaScript页面、TypeScript规则、Vite；并非React。`src/main.js`、s001模块已实际实现报销/审核/审批/历史，不只是静态按钮 | 原持久化和身份仍是浏览器演示 |
| R001—R004 | 原纯函数真实运行；住宿标准、票面重复、金额支持、抬头税号比较及证据已完成 | 可复用计算，原浏览器数据来源/角色不能当生产权限 |
| R005—R008 | 原科目、审批附件、预算和版本配置有业务逻辑与测试 | 浏览器规则和流程保留，不直接宣称服务端预算或正式入账 |
| R009 | 明确标记的本地关键词/场景演示，没有真实大模型 | 不接入本次正式业务，不上传财务资料给模型 |
| R010 | 浏览器Tesseract/PDF文字层、可选本机RapidOCR Python服务 | Python仅识别服务，无多人认证/数据库，不作为业务后端；本次不重做OCR |
| S002 | 真实运行的隔离实验、盲标/计时工具，冻结版本和样本 | 不作为正式台账或自动审批；保留冻结源和原数据 |
| 账号/文件 | 模拟角色，localStorage保存单据和部分base64原件；文件确实有字节，不只是名称 | 不能跨设备可靠协作，前端可修改角色/数据，无服务端范围权限 |
| 部署 | Vite构建、GitHub Pages静态分支 | 只承载演示，不能运行本次PostgreSQL/认证后端 |

本轮没有删除旧模块、旧库或旧模拟数据，也没有把旧批准/付款状态强行转成真实状态。业务模式仍使用同一仓库、同一个index入口和已有页面风格；后端返回业务模式标记，前端只加载业务UI。静态站点仍加载原演示入口。模式标记不是权限控制，真正权限来自数据库账号与服务端检查。

## 改造后数据流

Chrome同源HTTPS → Express5 → PostgreSQL事务/范围权限 → 私有文件目录。浏览器不再存放正式报销和登录令牌；登录Cookie HttpOnly/SameSite，生产必须Secure。`express-session + connect-pg-simple`存储会话；Argon2id保存密码，密码不存明文、不返回前端。首次登录必须更改管理员发放的初始密码。

员工手工录入→DB草稿与原件→提交锁定直属主管/部门/职级/公司制度快照及发票占用→主管→财务→待付款→付款登记。每次编辑有单据版本，每次处理有不可变操作记录，财务/付款不因原规则PASS而自动执行。

## 表结构（server/migrations）

| 表 | 主要字段/约束 |
| --- | --- |
| company | 单公司id=1、登记名称/税号、政策JSON、递增政策版本；不自动导入虚构企业和住宿标准 |
| departments | UUID主键、名称唯一 |
| users | UUID、唯一小写登录名、Argon2哈希、受约束角色数组、部门/直属主管外键、职级、active、强制改密、auth_version；主管不能为本人 |
| sessions | express-session随机会话ID、会话JSON和到期索引；登录会换ID，权限变更/停用使旧会话失效 |
| claims | UUID、序列生成单号唯一、员工/部门/主管外键、状态CHECK、revision、BIGINT分金额上限、CNY、规范化JSON快照、提交时间 |
| expense_lines | claim外键、费用类型、DATE发生日、BIGINT分金额、业务说明 |
| invoices | claim外键、规范标识、票号文本、BIGINT分、票面元数据；单内标识唯一 |
| invoice_lines | 明细与发票复合外键、分摊整数分；同关系唯一；服务端检查每张票分摊不超票额 |
| invoice_occupancy | 规范标识主键、claim外键；事务内原子占用，不靠前端字符串比较处理并发 |
| attachments | UUID、claim/line外键、用途、原文件名、实际类型、字节数、SHA256、上传人/时间、解除时间；不公开文件路径 |
| claim_versions | claim+revision唯一、原资料JSON、人员/原因/时间；数据库禁止更新/删除 |
| operations | 单据版本、操作人及当时姓名、实际角色、决定/说明、前后值、时间；只追加，应用账号无更新/删除权限 |
| payments | 单据唯一、整数分、DATE日期、方式/参考号、财务、备注、私有凭证外键；只追加 |
| payment_corrections | 原付款外键、财务、日期/方式/参考号更正、原因；原金额不被覆盖 |
| payment_references | 原付款和更正共享参考号唯一约束，防止跨表复用 |
| legacy_imports | 完整旧备份哈希/保留文件、上传人、预览、提交时间；来源与新草稿唯一关联 |
| schema_migrations | 有序迁移名、SQL的SHA256、应用时间；已执行迁移改写会失败 |

日历记账日与日期筛选使用Asia/Shanghai；时间戳以timestamptz保存，金额为整数分，避免UTC凌晨误判付款日期。数据库运行账号qb_app与迁移owner分离；前端无DB凭据。migration脚本只向应用开放必要表访问，审计/付款等禁止更新删除；外键与CHECK约束配合服务端事务使用。

## 权限

- EMPLOYEE：只能创建和编辑本人DRAFT/RETURNED，查看本人进度、附件及历史；不能直接更改状态、角色、审批或付款。
- MANAGER：仅当前分配给自己的待审批单可通过/退回/驳回；可看自己历史动作；非当前授权的后续资料不额外开放。
- FINANCE：可见进入财务环节及已由财务处理的单据，进行复核、足额付款登记、授权台账导出；不可批准或登记本人的单据。
- ADMIN：账号、部门、直属关系、公司政策与旧数据显式迁移。管理身份不自动等于所有员工财务资料的阅读权；如确需财务职责，必须显式分配FINANCE。

角色可兼任，但不能审批本人；首版未强制“主管”和“财务”必须不同账号，真实试用应分别配置。停用有待办任务的主管前必须重新分配。只有当前权限允许才能访问附件；历史操作页不绕过后续资料范围权限。

## 状态与并发

DRAFT/RETURNED → MANAGER_PENDING → FINANCE_PENDING → AWAITING_PAYMENT → PAID。主管或财务可退回RETURNED/驳回REJECTED。本人可关闭DRAFT/RETURNED为CANCELLED；REJECTED/CANCELLED不能由前端恢复。提交后不可任意编辑。已付不可普通修改金额或删除。

草稿修改用revision乐观锁，处理/提交/付款锁定单据行。发票身份全局占用主键在同一事务插入；不同单竞争只成功一个。退回保持占用，重提排除自己；正式关闭/驳回只有公司明确允许releaseOnClose时释放。原件、版本、原审核与操作均留痕。

付款仅一次性足额登记，单据和参考号唯一，重复相同请求返回原有结果，不产生新付款。更正只追加日期/方式/参考信息及原因；分期、差额支付、冲销退款和金额更正未实现，不得用该接口伪造转账。

## 规则适配

直接复用原registry/auditAll、R001/R002/R003/R004与R003既有policyOutcome。服务端按费用明细和发票分摊组装原Input，按单公司登记基准和已保存制度构建上下文。R003非住宿范围由明确保存的服务端费用类型政策适配，不修改冻结原规则。R005—R008原演示保留，正式业务不声称已具备完整服务端预算、凭证或复杂审批树。

自动结果保留原规则号、每条明细、制度版本、原始依据及查重冲突。财务批准时重新执行；BLOCK/ERROR/资料不足不能普通批准，REVIEW需要财务核查并填写意见。非财务角色的R002历史冲突证据去除其他员工详情；原件内容仍须财务人工对照，不证明发票真伪。正式业务无大模型服务和外部OCR上传。
