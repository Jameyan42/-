# R010 使用、验收与限制

## 浏览器演示流程

1. 按 [本机服务说明](../../services/invoice_ocr/README.md) 启动，Chrome打开 `http://127.0.0.1:8766/?view=claims`。在线现有站点也能体验文字层PDF和浏览器后备OCR，但不能运行Python模型。
2. “新建报销单”，填写报销人和部门，选择住宿费、填写申请金额1060；“添加发票”，上传 `public/samples/r010/01.png`。上传即自动识别，不需要再点击重新识别。
3. 检查号码、日期、买卖方、净额1000、税额60、合计1060、项目名称。展开 R010 对照表与结构化JSON，点击“查看 / 下载原件”打开本地原件。
4. R002、R003、R004即时预审会自动执行。未填写报销人/部门时R002可能资料不足；未选择法人或购买方信息待核对时R004不能当作正常通过。保留原规则，不用OCR结果替代人工确认。
5. 修改合计为1061，查看R003从金额一致变为提醒部分报销；点击“已对照原件逐项核对”，再保存草稿。重新编辑可见原始1060和修正1061，以及确认人、时间、文件SHA256。
6. 再次编辑已确认票面会恢复“待核对”，需要重新确认；旧原始结果、此前确认快照不覆盖。正式审核仍点击“开始自动审核”，原有业务审批、预算、财务复核要求全部保留。
7. 加第二张同一张样票：R002提示重复风险。换为02.pdf验证PDF_TEXT且不调用模型；08.pdf验证扫描件实际调用本机OCR；11.png验证缺失净额/税额保持空白，不做倒推。

## 结构与数据流

浏览器原件 → PDF文字层或CPU/浏览器OCR → 共用保守字段提取 → 原始JSON和原件SHA256 → 可编辑原有发票字段 → 原R002/R003/R004只读即时预审 → 人工核对 → 原有保存/提交链路。

`src/r010/recognize.js`选择实际识别路径；`extract.js`只提取有依据的字段；`capture.ts`分别保存原始识别、当前修正、最近确认快照；`preview.ts`直接调用原registry，不写预算、审批或审核批次。`src/s001`仅扩展可选字段和界面，旧历史数据不补写OCR字段，R001—R009核心规则不修改。

原件与OCR记录放在现有浏览器 `qingbao-s001-v1`。刷新保留已保存草稿；未保存离开仍提示。不是服务端数据库、真实账号权限或防篡改审计。现有全局备份并不包含S001/R010数据，清站点缓存会丢失，不把它描述成已有正式归档。

## 限制

- 仅本轮R010，不增加其他财务模块。当前仍是单机演示，不能直接用于200人企业正式财务操作。
- 每个原件1MB、每单总1.5MB、5张票、最多20页PDF，选择其中一页处理；本机JSON图像有大小/像素上限。沿用原件限额，不为OCR放宽原有内控。
- 每票最多3次原始识别，达到限制后明确提示，禁止覆盖旧结果。更换原件后，旧OCR结果、文件名、哈希留存，但旧原件字节不另行历史归档；查看原件按钮打开当前附件。
- 每次成功识别填入当前票面，无法可靠提取的字段留空，不沿用上一张票的金额/税号；处理期间用户编辑过的字段保留。识别失败不清空已有手工资料。
- 原始结果不可被“修正”操作改写；保存修正是当前值快照，不是逐次键盘编辑日志。角色和时间是本地模拟记录，不能作为合规审计凭证。
- 原始票种文本保留；映射到已有票种选项。OCR每行分数只作关联字段的低置信提示（阈值0.90），不是正确率。PDF文字层/浏览器后备没有可靠逐字段分数时显示未知，不伪造分数。
- 未识别、候选冲突、负数/异常号码需人工处理；无法自动保证所有省份、年代、手写、拍照反光、印章遮挡、红字票、复杂多商品表格或同页多发票。多页不自动拆票，不做税务平台验真。
- PDF有文字层不代表字段可信，也可能文字层与视觉内容不一致，仍应对照原件。本期选择一页，不证明其他页无重复或附件齐备。
- 本机服务仅本机CPU运行；静态GitHub Pages保持PDF.js/Tesseract后备。不能把云端localhost当作用户电脑链接。
- PaddleOCR3.x权重下载失败，原生3.x推理尚未验证；默认RapidOCR已验证。Windows路径已说明，Windows实机尚未验证。
- 当前只有12份独立预设字段的虚构样票，尚未完成足够真实脱敏发票的准确率验证。样票匹配不等于真实业务“完整识别率”。
