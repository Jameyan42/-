## R003规则与数据边界

- 一次性付款检查验收完成、报告、合同余额；分阶段检查当前阶段限额/已支付/前置证据，不推导上阶段付清才可支付；结算模式同时检查合同和已确认结算余额、结算单。
- 只统计“已支付”为真实累计；“待支付”单列，并检查已支付＋待支付＋本次的合同、阶段及结算占用。已取消/支付失败不占用。按申请编号排除自身，其他申请全部比较。
- 合同不存在、金额/日期/阶段或历史基础数据无效：优先报错，不计算虚假金额。所有可可靠判断的业务风险一次性返回；合同草稿、终止、到期、未生效、缺证据/无效证据、超额或0元均转人工。
- 金额统一整数分，比例整数基点，BigInt中间计算；前面阶段按分四舍五入，尾差归最后阶段，合计等于合同总额，无法合理分配的配置拒绝保存。历史已支付超额单独报异常，可用余额显示0。
- 审核基准日期由调用方传入；测试固定2026-10-25，种子首次创建或恢复按传入年份设置有效期，刷新不修改既有日期，真实旧合同仍可能到期并转人工。
- 每单版本保存合同/阶段/付款/证据/计算/风险快照；同单重审追加版本，用最新本地数据。人工姓名原因必填、仅最新待复核可操作，一版本不重复处理。
- 独立键`qingbao-r003-v1`，首次成功操作保存，刷新不覆写；保存前读取最新数据并作旧值冲突检查。恢复经确认只替换R003合同和付款库，保留申请及全部版本，绝不写R001/R002键。损坏数据暂停，配额/冲突保留原数据及输入。
- 容量：合同/付款/单据各200笔、每单20版本、JSON220万字符；浏览器可能更早触及配额。纯前端无跨账号事务、自动资金锁定、防篡改或生产权限。审核不会自动生成待支付或已支付记录，模拟历史付款需在管理区维护。
- 不上传文件；证据状态只代表模拟业务记录，不证明附件真实、合同合法、真实交付验收或已付款。没有新增OCR/AI、银行、ERP、合同系统接口或R004。只用虚构数据。

## 查重判断与数据约定

| 条件 | 处理 |
|---|---|
| 同类型、代码与号码均一致 | R002-01票面标识重复，转人工 |
| 双方均为无代码数电发票、完整号码一致 | R002-02票面标识重复，转人工 |
| 同号码但类型不同，或代码有无不对称 | R002-03潜在标识冲突，转人工，不直接认定同票 |
| 同类型传统发票、号码相同但完整代码不同 | 不判定精确重复；若无其他风险通过R002 |
| 传统电子/纸质发票缺代码 | 待补充，不执行可靠查重 |
| 其他类型无可靠标识 | 人工复核 |
| 没有匹配且标识完整 | “未发现当前模拟历史记录中的重复发票” |
| 缺必填、无效日期、负金额、三位小数、金额格式或安全整数越界 | 待补充/数据错误，不执行可靠查重 |
| 0元 | 提示金额异常，需人工确认，不仅凭金额判重 |

发票标识只作为字符串规范化：去前后空格、NFKC全半角统一、保留前导零和长号码，不转成数字；不依赖金额、姓名、销售方同名来判重，不做官方号码位数真伪判断。提供的BX-H004号码为21位，按原文完整保留，同时测试20位前导零号码。

每笔命中显示关联单据及当时已通过/审核中/已驳回/已撤回状态；四种状态都转人工，驳回/撤回不自动放行。按**当前单据编号**排除自身，其他单据即便引用同一发票记录编号也会命中。金额在业务字段中以安全整数分保存，100.01元＝10001分，0.01元＝1分；原始金额文本另存用于数据错误提示，不参与浮点财务计算。日期复用R001公历校验。

自动结果有独立规则编号/版本、输入快照、时间、数据版本、查重范围计数及所有同号码候选快照（包括不同代码未命中的候选）。命中不是违规认定，“通过R002”也不等于整单已审批或已付款；新自动审核后业务状态仍为审核中，人工结论另外保存。

## 版本、存储与恢复

- 独立键`qingbao-r002-v1`，不迁移/重置R001的`qingbao-r001-v1`或原轻报数据。无旧R002专属存储需要迁移；旧轻报已有查重属于不同的模拟业务台账，未自动导入本规则数据范围。
- 初次无R002数据时提供5笔内存种子，首次成功保存操作后持久化；刷新读取现有数据，绝不重复覆盖用户修改。
- 重新审核追加v2、v3等，按最新本地历史重新计算；保存前重新读取localStorage，再查重并作旧值冲突检测。只保护当前可访问本地范围，不提供跨浏览器全局一致性或事务锁。
- 已可靠识别的同单票面类型/代码/号码绑定不覆盖；更换发票请新建单据。其他资料可更正后追加版本，早先资料不足可补齐后再审。若新版本有数据错误，前一有效版本的发票仍保留在后续查重范围，并标出有效版本号。
- 恢复需二次确认，只替换模拟库，保留R002全部单据、自动证据及人工记录，也不写R001键。可解析且仅历史库损坏时可安全替换该库；若JSON或单据证据损坏，拒绝恢复，不静默清空。
- 存储配额/权限失败保留原值和页面输入；未保存切页有确认，旧版本不覆盖新版本。仅本地数据没有防篡改保障，不把校验等同审计不可抵赖。
- 原型容量：模拟库200笔、R002单据200笔、每单20个审核版本、存储JSON最多220万字符，仍可能先触及浏览器配额；超限明确提示，不删除旧证据腾空间。

## T03完整演示

1. 进入录入页，点击“载入 T03 超标示例”：张晓（虚构）、普通员工、深圳、2026-10-20入住、2026-10-23退房，自动显示3晚，申请1800元。
2. 点击“执行自动审核”：匹配深圳普通员工500元/晚；限额 `500×3＝1500元`；超标 `max(0,1800−1500)＝300元`，自动结果为“需要人工复核”。
3. 进入人工复核，不填原因不能操作；填写“展会期间涨价，经核对批准此次例外（虚构）”后点“人工通过”，看到独立人工通过、原因和操作时间；原始自动超标300元结果仍可查看。

5. 标准管理把深圳普通员工改为700元/晚；回到旧单仍为500元和1500元限额。点击“复制为新单重新审核”，新单限额为2100元并通过本项，旧单不变。

## 正确性与数据约定

- `src/r001/rule.ts`为独立纯函数：无网络、存储、当前时间或随机编号；编号/操作时间由界面层传入。
- `types.ts`定义明确类型，TypeScript严格检查。金额业务字段均为整数分（`nightlyRateCents`、`amountCents`、`limitCents`、`excessCents`）；仅保留原始输入字符串 `input.amountYuan` 用于展示错误和复核，不用浮点数参与金额计算。最多两位小数，拒绝科学计数法和超安全范围金额，限额乘法也检查整数安全范围。
- 住宿晚数通过公历年月日序数计算，支持闰年和跨月/跨年，不用毫秒差除以24小时。退房日不计住宿晚数，退房必须晚于入住。
- `申请≤限额`通过本项，`申请>限额`转人工；只按多晚总金额判断，不臆测逐晚费用。
- 未配置城市/职级组合：人工复核，限额和超标金额均为`null`，界面显示“无法计算”，不虚构0元标准。
- 必填缺失为“待补充资料”，无效日期、负数或格式错误为“数据错误”；均不执行超标判断。0元申请单独转人工确认，已匹配时超标为0，不误报超标。
- 每单保留标准版本、更新时间、所查城市/职级及当时金额；缺标准也保留当时未匹配的事实，之后补标准不改旧结果。
- 仅中国境内、人民币、单城市连续住宿；维护者应仅增加境内模拟城市。不支持多城市拆分、外币、真实性核验或整单报销审批/支付。

## 本地保存及失败保护

唯一新增localStorage键：`qingbao-r001-v1`。首次提供2笔虚构样例，数据在首次操作保存后可刷新继续查看。浏览器清理会丢记录，无后端或跨设备同步。模拟财务身份没有生产鉴权或审计防篡改保障。

本地记录加载时按**历史标准快照**复算一致性；损坏数据不自动覆盖，提示恢复。存储配额失败保留表单和原值；复核须明确操作并填写原因；检测到其他页面已写入时拒绝用旧状态覆盖，提示刷新（这不是后端原子并发控制）。标准/复核未保存切换可取消。原型容量为200笔记录、300条标准和约150万字符。

## v0.15：差旅行程、费用明细与示例标准

本轮连通三个功能：出差申请补充出发地、目的地、出发/返回日期、城市档和示例职级档；差旅报销可启用1～20行费用明细（城际交通、住宿、餐补、市内交通、其他），自动合计；按固定版本示例标准检查住宿和餐补，超标说明必填后交由人审核。新增只读“差旅标准”页解释金额及口径。

员工 → 费用申请 → 新建，勾选“这是出差行程申请”；按原申请审批路径批准并预留预算。员工新建报销，选择本月已批准申请时自动载入行程并启用差旅明细；报销的行程和批准申请必须一致，关联金额仍受剩余额度硬限制。未关联申请也可手动启用差旅明细。旧普通报销不强制补填。

示例演示：林晓申请杭州至上海10月21～23日、2000元；赵航批准。关联报销填住宿1000元/2晚、餐补300元/3天、城际交通200元，自动合计1500元；主管→财务审核→模拟付款，申请剩余500元，付款后可结束申请释放未用余额。另填住宿1100元/2晚，显示超过500元/晚，要求说明后提交，审核人在详情查看超标与理由。

这是自定义示例制度，不代表法定标准或真实企业政策。城市/职级档手工声明，未接HR；标准只读，版本travel-demo-2026-01。住宿按实际晚数、餐补按含首尾自然日；重复住宿/餐补日期、越界日期、合计不一致会被拒。跨月行程暂需拆分，批准申请只在报销归属月份一致时可关联；报销日期仍沿用原提交/原单日期，不按行程自动改预算月份。

超标说明不自动豁免审批或原有单笔上限、缺附件、重复号码检查。明细行金额是行合计，不支持逐票附件、多票OCR、发票验真、自动订票或真实支付。启用差旅后的草稿也需完整行程及明细；可关闭差旅模式继续普通草稿。JSON备份保留行程、明细、理由和版本，非法合计/行程拒绝导入且不覆盖原数据。


## v0.16：费用申请进度与额度追踪

员工 → 申请进度（费用申请列表也有入口）。按待审批、已批准、已驳回、已关闭和计划月份筛选，搜索事项/单号/费用类型/目的地/当前审批人；每页10条，改变筛选回到第一页，切页面或身份清空筛选。概览始终统计本人全部申请，当前匹配数单独显示；导出CSV包含全部匹配页和本次筛选条件。

待审批按提交快照展示具体人员和顺序节点；旧申请只显示原主管角色，状态与路径不符时不猜处理人。批准后显示已占用额度、在途报销、已登记付款、未使用额度、当前可关联和余额预留。已占用=在途+已登记付款，草稿/退回/撤回不占额度。只有已批准的未使用余额可关联并预留；关闭或驳回的未使用金额仅供回顾，当前可关联和预留均为0。付款登记仍不等于银行到账。

卡片可展开本人关联报销并打开详情，显示不占额度的退回/撤回/草稿；从申请详情按原规则结束申请，仍有在途报销则不能结束。驳回显示原因，本版申请仍不可修改重提，可另行创建。出差申请展示已有行程。新记录按申请人ID归属，旧记录以唯一姓名和部门兼容；申请详情增加本人校验，演示身份不等于生产认证。

演示：林晓申请1000元→赵航批准→关联600元报销；申请卡片在途600、可关联400、余额预留400。员工撤回600元，卡片在途0、可关联1000；结束申请后未使用1000仍可回顾，但当前可关联/余额预留均0。另一条路线完成模拟付款后显示已登记付款600、余额预留400，结束只释放400。申请批准不等于已支出1000，不将原额度与在途重复计入预算。

页面为只读进度与现有操作入口，不迁移或清理数据。存储损坏明确提示且不展示假完整概览/导出。没有催办、自动超时、消息通知、跨设备同步或生产访问控制；筛选和导出不写入业务数据。


## v0.17：报销多附件与证明材料

新建/编辑报销 → 报销附件 / 证明材料，可多选上传PDF、PNG、JPG、WebP，并分别标为发票、酒店水单、行程单、付款凭证或其他材料。每单最多5个，单个1 MB、合计1.5 MB；为浏览器演示版容量限制。原文件保存在报销记录中，不上传外部服务；保存草稿、刷新、退回修改后仍保留。旧“发票OCR / 原票据名称”入口继续兼容，但该入口本身仍只记录名称；需保留原文件时使用新附件区。

完整JSON备份包含附件原文件（编码保存），恢复后仍可下载；旧仅名称记录不补造文件。导入检查分类、数量、扩展名/类型、文件头、编码、大小与单据总容量，非法数据不覆盖原数据。备份仍限制5 MB；浏览器总容量不足会提示。保存报销先写成功再更新内存；备份多键恢复写入失败时尝试回退已写入键，原测试数据回退已验证，异常无法回退时明确提示。

演示：员工填写200元报销，旧OCR入口选择发票；新附件区上传虚构酒店水单PDF和行程截图PNG，分类后保存草稿。刷新再编辑提交，切主管查看两份材料，展开图片并下载PDF。导出备份并在独立测试环境恢复，原PDF字节一致。请用虚构材料，备份含原文件，应由用户自行保管。

当前为本浏览器本地存储，不跨设备同步；清理浏览器数据会丢文件。图片只支持预览，不编辑原图；PDF不内嵌预览。文件头检查不是恶意文件扫描，也不能保证票据真实。没有云文件服务、细粒度下载授权、加密存储或永久留存承诺。


## v0.18：付款清单、重复参考号与批量模拟登记

付款工作台新增当前筛选清单CSV导出、勾选/清空和批量模拟付款。只可选择本人有权限的待付款单据，每批1～20笔，切筛选/搜索/页面/身份会清空勾选；超过20笔需缩小查询或手选。管理员仍只读。原搜索支持事项、单号、申请人、部门和参考号，导出包含当前筛选的所有记录，不只勾选项。

点击批量模拟登记，预览逐笔事项、金额、单号和参考号，并填写日期、方式、备注。前缀为3～48位字母/数字/下划线/短横线，每笔生成“前缀-001”等独立模拟参考号；明确确认仅模拟后才能提交。重新校验所有所选单据的状态、具体付款权限、schema2总账信息、预审风险、参考号和付款字段，其中任一失败整批不保存。单键保存成功后才更新界面；容量不足保留原单据及核对表单，可减少问题后重试。

成功后每笔报销保留独立付款信息和具名处理记录，批量操作另记一条操作日志，刷新与完整备份兼容。导出包含部门、申请人、金额、状态、付款责任人、总账科目、核算归属、付款日期/方式/参考号及筛选条件。仅是模拟登记，不连接银行、不确认到账、不生成实际银行付款文件。

演示：按已有财务分工模板提交两笔200元报销，经部门负责人、财务、总账完成后切杜川→付款工作台，勾选两笔→预览合计400和两个参考号→确认模拟→查看已付款及审批中心我已处理两条记录→导出清单。再以相同前缀登记新单据，观察重复拦截；核对失败不部分登记。旧流程仍由原财务办理。


## v0.19：站内消息中心

新增消息中心及导航未读角标，按当前人员展示本人应处理的报销/申请、待付款任务，以及本人单据的退回、待付款、已登记付款、申请批准/驳回/关闭结果。消息从当前浏览器单据状态派生，每单只展示当前一条提示；旧记录也可能初次出现，不代表新发送。完整历史仍在单据流转记录。

支持类别、未读和关键词联合筛选，每页20条；单条标为已读、将当前全部匹配页标为已读、点击消息打开对应单据。已读按人员ID分别保存，刷新保留，切身份清空筛选；查看单据时尝试标已读，保存失败会提示但仍可查看业务。标已读不改变审批中心待办、报销/申请状态或额度。

消息标识包含单据类型、ID、当前状态、本次提交标识、节点和流转记录版本线索；不变的状态稳定复用已读标记，进入新节点或退回重提后是新未读。过期待办不留在本页，不构建独立的消息投递日志。按具名快照确定当前处理人，旧单仅按原角色匹配，不猜人员和时间。

已读状态随完整备份保存；新备份恢复时恢复已读，旧备份缺少已读字段则保留当前已读。格式错误拒绝导入且不覆盖原存储。已读损坏时显示未知、禁标记，保留原始值；申请存储损坏时明确只显示可读取报销消息、总数不代表完整结果。已读写入配额失败不改变原状态。每人最多1000条、总量最多20000条且序列化40万字符保护，达到上限不自动清空旧标记。

演示：林晓提交报销→赵航消息中心查看具名待办并标已读，审批中心待办仍在→从消息打开退回写“补酒店水单”→林晓看到退回提示并修改重提→赵航看到新的未读任务。再用申请批准/模拟付款结果查看员工进展提示，标已读后刷新核对。仅站内展示，不发送短信/邮件/系统通知，不在后台跨设备投递或自动催办。

此功能不是此前“AI开发任务完成后弹窗”配置，开发完成系统提醒仍未配置。没有消息服务、服务端权限、推送到达率或真实用户收益数据，身份选择仍为演示机制。

## v0.23：原件关联与对公履约附件

报销和对公均可保存发票、酒店水单、验收单、合同附件等材料。在附件区选择“发票”并上传后，票面采集可选择该原件，从图片运行本地OCR，或关联PDF后手工核对。审核详情从票面卡片直接预览图片/下载原文件；已关联文件须先解除票面引用，再移除或改类。字段JSON只含引用，完整备份包含原件。

每单最多5份、单份1 MB、合计1.5 MB；对公元数据保留原80万字符上限，含文件总量220万字符保护，浏览器配额失败不覆盖原值。旧字段无引用继续兼容，不按同名文件猜测关联。每个原件限一张票面，多票合并文件需拆分；逐费用明细分摊、官方验真、PDF自动识别与对公统一待办仍未实现。详见[原件关联与对公附件设计](docs/原件关联与对公附件设计.md)。

## v0.24：对公统一工作台

审批中心新增对公类型及每页20条统一待办，从原页面直接打开对公详情办理；“我已处理”保留新操作的处理时事项、金额和总账/付款摘要，并支持日期筛选和全匹配CSV。消息中心汇集对公待办及本人进展，支持单据类型筛选、逐条/跨页已读和直接办理，已读不改变审批。重提更换路径后，原具名处理人可只读回看当前单据，不能继续处理新节点。

旧对公日志不补造处理快照，备份兼容旧记录；数据集合异常时明确部分结果、角标未知并暂停假完整导出。对公批量付款、合同复核待办、短信推送和跨设备协作尚未接入。详见[对公统一工作台设计](docs/对公统一工作台设计.md)。

## v0.25：预审风险逐项核对

报销和对公详情支持当前节点处理人对命中疑点追加“已核对 / 待补充 / 建议退回”、5～500字说明及一份本单材料关联。后续节点可回看人员、当时规则依据、金额和提交轮次；记录独立于审批，不改变状态或豁免拦截。单据、原件字节、规则或重提依据变化时提示重新核对，正常节点推进仍可沿用说明。

历史可导出CSV并随完整备份保存，旧数据无此字段继续兼容；每单100条/40万字符保护，失败保留输入和原值，未保存核对有关闭与审批保护。这是本地变更检测与人工说明，不是AI、官方验真或不可篡改审计，未实现风险豁免及材料补交任务。详见[风险逐项核对设计](docs/风险逐项核对设计.md)。

部门预算按月份独立设置额度和软预警/新增占用拦截；普通报销提交和申请最终批准时检查新增，已有预留核销、付款不重复扣减。可从汇总下钻贡献明细、查看单据及导出全部匹配页，调整留存具名原因和版本，新旧备份兼容。详见[预算设计](docs/月度预算与新增占用管控设计.md)。对公仍按合同额度，未加入部门预算。

## v0.27：PDF 发票识别

新建报销的快速OCR，以及报销/对公的结构化发票采集均支持PDF。选择文件后先预览、选页，每次识别一页；同源PDF.js转图后用现有Tesseract.js提取，电子文本PDF和扫描PDF走同一人工核对流程。新增公开虚构PDF样票（第2页发票），可从识别区下载。

文件仍留在浏览器；最多6 MB、20页，不能保证通用版式准确率。需留存原件时先在附件区上传（原限制1 MB/份、1.5 MB/单不变）并分类为发票，再选择原件识别；每原件限一张票面，多票合并文件请拆分。详情下载、备份、旧数据保持兼容。详见[PDF设计与演示](docs/PDF发票识别设计.md)。


## v0.28：按城市与人员职级的差旅预审

财务→差旅标准可维护城市目录、两档城市×两档职级的住宿/餐补/市内交通标准、单城市特例和人员ID职级，填写原因发布。员工填目的地后自动匹配，不能自行选高档；未知城市和未维护职级明确提醒。新差旅报销保存适用标准快照，制度调整不追改在途；退回重提才用新标准，旧无快照单据提示核实原制度。

系统预审住宿、餐补、市内交通（同日多行合并），展示标准计算、实际金额、超额；同时检查缺酒店水单、未关联事前费用申请。默认提醒，可设为拦截财务/总账/付款；超标说明和“已核对”不豁免，仍需人工审批。示例：上海普通员工500元/晚，住宿1100元/2晚→标准1000、超额100元；管理档700元/晚，其他城市普通档350元/晚，均可按虚构制度修改。

本阶段以透明规则减轻重复核算，不依赖OCR，暂停继续扩展通用OCR。没有真实HR、自动水单内容核验、真实银行付款或生产鉴权；金额不代表法定标准。备份保留制度和快照，旧备份缺制度保留当前版本，配置/快照损坏不视作通过。详见[差旅城市职级预审设计](docs/差旅城市职级预审设计.md)及阶段验收；README中的设计文件位于docs目录。
